# HERO HUD — 설계 전략

작성 2026-08-05 · 권우진
대상 마감 2026-08-18 (HERO 7주차)

이 문서는 결정된 것과 그 근거를 적는다. 아직 재보지 않은 것은 "미측정"이라고
적는다. 상위 프로젝트의 공학 기록은 `hero-carla-vision/docs/시뮬레이션_비전전환_진행상황.md`이고,
이 문서는 그 위에 얹히는 표시 계층만 다룬다.

## 0. 무엇을 만드는가

저시력 운전자(조아영, 양안 교정시력 0.1)가 직접 운전하는 동안, 시스템이 인식한
것을 윈드실드 HUD로 보여주는 표시 계층. **차량 제어 개입은 없다.**

**주차만이 아니라 주행 중 보조도 맡는다**(2026-08-11 정정). 이 문서의 13절까지는
주차 기동만 전제로 쓰였고, 그 전제가 숫자에 그대로 박혀 있다 — 코리도 범위 6 m,
경로 8 m, 급함 판정 3 m, 거리 눈금 0.3/0.6/1.0 m 는 전부 1.5 m/s 언저리에서
고른 값이다. 주행 속도에서 무엇이 되는지는 13-47 에 적었다. **아래 절들을 읽을
때 그 값들이 주차 전용이라는 것을 염두에 두어야 한다.**

07-07 방향 조정 자료에 **"장면 정합 X"** 라고 적혀 있다. 실세계에 픽셀 단위로
겹치는 AR HUD가 아니다. 아이박스 캘리브레이션·헤드 트래킹·지연 보상이 전부
요구사항에서 빠지고, 남는 것은 **고정 가상 카메라로 그린 상징적 투시 뷰**다.
그것은 3D 엔진 없이 호모그래피 하나로 끝난다.

## 1. 설계를 지배하는 제약 다섯

1. **장면 정합 없음** → 3D 엔진 불필요. 고정 3×3 호모그래피.
2. **저시력 사용자가 1차 사용자** → 픽셀이 아니라 시각(視角)으로 설계한다.
3. **컴바이너 가산광** → 검정이 투명이다. 면 채우기가 곧 시야 가림이다.
4. **부팅 즉시 표시** → 데스크톱 환경 없이 DRM/KMS 직행.
5. **인지 품질의 상한이 이미 측정되어 있다** → HUD가 주장해도 되는 것의 한계가
   설계 전에 정해져 있다. 3절.

## 2. 입력 — 센서 5개

| 입력 | 용도 | HUD와의 관계 |
|---|---|---|
| 전방 카메라 (30° 하향) | 지면 오도메트리 · 점유지도 | 간접 |
| 후방 카메라 (30° 하향) | 지면 오도메트리 · 점유지도 | 간접 |
| 세 번째 카메라 | 차선 · 신호등 · 표지판 (고영우) | 간접 |
| IMU | yaw · 자세 | 간접 |
| **CAN** | 기어 · 속도 · 조향각 | **직결** |

기존 두 대는 30° 하향이고 상위 문서가 *"어느 거리에서든 대략 1 m의 월드 높이를
본다"* 고 재놓았다. 그 기하로는 신호등과 표지판을 물리적으로 볼 수 없으므로 세
번째는 전방 수평 시야일 것으로 본다. **미확정 — 고영우와 확인 필요.**

주기 예산은 카메라마다 다르게 잡는다. 오도메트리용 두 대는 60 Hz가 필요하지만
신호등·표지판은 준정적이라 10 Hz면 충분하다. 균일하게 돌리면 Orin에서 낭비다.

## 3. 정직성 규칙 — 이것이 곧 안전 설계다

상위 문서가 이미 측정해 놓은 것:

- 차 재현율 최고 **0.603** (21-5). 주차된 차 셀의 40%를 놓친다.
- *"지금 점유지도 품질이면 어느 방향에 장애물이 있다 수준의 코칭은 가능하고,
  거리 수치를 말하기엔 이르다."*
- 전방 정밀도와 후방 정밀도가 두 배 이상 차이 난다 (16-8, 17-5).

그래서 표시 규칙 넷을 **설계 전에** 고정한다.

1. **심볼이 없는 것은 "안전"이 아니다.** 빈 공간을 초록으로 칠하는 식으로
   "여기 비었음"을 적극적으로 주장하는 표현을 금지한다. 40%를 놓치는 지도 위에서
   저시력 사용자에게 이것은 직접적인 위험이다.
   → 가산광에서는 이 규칙이 공짜로 성립한다. 안 그리면 물리적으로 투명이고,
     가산광 디스플레이는 "비었음"을 주장할 방법이 애초에 없다.
2. **거리는 숫자가 아니라 띠로.** "2.1 m"가 아니라 "가까움 / 매우 가까움".
3. **출처를 표현에 반영한다.** 전방 유래와 후방 유래를 시각적으로 구분한다.
4. **신선도가 떨어지면 단계적으로 물러난다.** 6절.

## 4. 시각 언어 — 가산광이 확정한다

검정이 투명이라는 것은 색 제약이 아니라 표현 문법 전체다.

| 규칙 | 이유 |
|---|---|
| 클리어 컬러는 정확히 `#000000` | 짙은 회색도 빛으로 나가 흐린 사각형이 뜬다 |
| 면 채우기 금지, 외곽선만 | 채운 면은 그만큼 전방 시야를 가린다 |
| 그라디언트 · 그림자 · 글로우 금지 | 저휘도 구간이 외광에 먼저 사라져 형태만 뭉갠다 |
| 최소 획 두께를 **각도**로 하한 설정 | 얇은 획은 외광에 소멸하고 이중상에 취약하다 |
| 프리멀티플라이드 알파 | 배경이 없으므로 검정 위 블렌딩이 곧 물리 모델이다 |

**색은 2차 채널이다.** 눈에 도달하는 것은 휘도뿐이고, 여기에 저시력 요구(색 단독
인코딩 금지)가 겹친다. 정보 부호화 순서를 고정한다.

> 휘도 → 굵기 → 형태 → 위치 → 점멸 → (마지막에) 색조

색은 흰색 / 앰버 / 적등 정도의 좁은 집합으로 제한한다. **청색 계열은 쓰지 않는다** —
시감 효율이 낮아 같은 밝기에 출력을 더 태우고, 유리 반사에서 색분산이 가장 눈에
띈다.

## 5. 두 개의 신뢰도 계층 — CAN이 현재궤적을 인지에서 떼어낸다

이것이 이 설계의 중심 판단이다.

**현재궤적은 인지 스택이 전혀 필요 없다.** CAN 조향각과 휠베이스로 자전거 모델을
풀면 끝이다. 회전반경 `R = L / tan(δ)`, 후륜축 중심이 그리는 원호. 후방카메라
주차 가이드선이 오래 쓴 계산이고, CAN 주기로 나오고, 지연이 사실상 0이며,
**비전이 죽어도 살아 있다.**

이상궤적은 인지 + 목표 pose + 계획이 모두 있어야 나온다.

| | 출처 | 가용성 | 저하 시 |
|---|---|---|---|
| **현재궤적** | CAN 조향각 | 부팅 직후부터 항상 | 유지 |
| **이상궤적** | 인지 + 계획 | 인지가 살아 있을 때만 | 사라짐 |

따라오는 결과 셋:

- **저하가 저절로 설계된다.** 인지가 죽으면 이상궤적과 장애물이 사라지고
  현재궤적만 남는다. 깨진 화면이 아니라 정직하게 축소된 화면이다. 사용자는
  "시스템이 지금 무엇까지 아는가"를 화면 구성만으로 읽는다.
- **부팅 요구사항이 풀린다.** CAN만 붙으면 HUD는 즉시 의미 있는 것을 그린다.
  인지 노드의 수렴을 기다릴 필요가 없고, 검은 화면 구간이 사라진다.
- **기어가 HUD의 모드 선택자다.** R이면 후진 주차 모드, D면 전진, P면 대기.
  이것을 인지에서 추론하려 들지 않는다. CAN이 그냥 알려준다.

### 조향비

CAN이 주는 것은 보통 **스티어링 휠 각도**지 조향륜 각도가 아니다. 조향비를
재야 한다. IONIQ Electric 휠베이스 2.700 m는 상위 문서 17-8에 있다. 조향비는
실측이 빠르다 — 정지 상태에서 락투락 대비로 잡거나, 일정 조향으로 원을 그려
반경을 재면 된다. **미측정.**

## 6. 저하 상태 넷

| 상태 | 조건 | 화면 |
|---|---|---|
| 대기 | 부팅 직후, CAN 없음 | 정적 프레임 + "연결 대기". **검은 화면 금지** |
| 기본 | CAN만 살아 있음 | 현재궤적 + 기어 + 속도 |
| 정상 | 전 소스 신선 | 전체 표시 |
| 신뢰 불가 | 포즈 상실 / 격자 정지 | 이상궤적·장애물 **철회**, 명시적 경고 |

크래시 후 재시작 중에 마지막 프레임이 화면에 남지 않아야 한다. 죽은 정보가
살아 있는 것처럼 보이는 것이 최악이다.

## 7. 아키텍처 — GUI / API 분리

```
                     [API 계층]                        [GUI 계층]
  /hero/vehicle_state ──┐
       (CAN, ~50 Hz)    ├─→ RosBridge ─→ HudState ─→ WorldItem  (QSGGeometryNode)
  /hero/scene_overlay ──┘   (rclcpp)     (최신값만)   ChromeItem (텍스트 텍스처)
       (인지, ~20 Hz)
                          ROS 실행기 스레드        Qt 렌더 스레드
```

### 원칙

- **렌더는 ROS를 기다리지 않고, ROS는 렌더를 기다리지 않는다.**
  경계는 `HudState` 하나이고 최신 스냅샷만 보관한다. 큐 없음.
  QoS는 전부 `best_effort` / depth 1.
  **HUD에서 오래된 프레임은 버린 프레임보다 나쁘다.**
- **HUD는 바보다.** 위험 판단, 시간 동기, TF 조회를 하지 않는다. 좌표는 전부
  `base_link` 지면(z=0)으로 들어오고, HUD는 프레임 변환을 모른다.
- **기하는 순수 함수다.** `projection.hpp`, `vehicle_model.hpp`는 Qt 의존도
  ROS 의존도 없다. 단독으로 테스트된다.

### 입력을 둘로 나눈 이유

앞의 "HUD는 메시지 하나만 받는다"에 **의도적인 예외**를 하나 둔다.
항상 살아 있어야 하는 신호를 가장 잘 죽는 노드에 묶으면 안 된다.
`hero_coach`가 크래시해도 HUD는 기어와 현재궤적을 계속 그려야 한다.
원호 계산은 HUD가 직접 한다.

### hero_coach (미구현)

인지 결과를 "화면에 그릴 것"으로 환원해 **한 프레임을 하나의 메시지로**
원자적으로 발행하는 노드. HUD가 여섯 개 토픽을 서로 다른 주기와 서로 다른
신선도로 렌더 시점에 화해시키는 일을 없앤다. 인지 쪽이 아직 심하게 요동치므로
(21장이 하루 만에 목적함수를 뒤집었다) 그 요동을 여기서 흡수한다.

## 8. 왜 이 스택인가

**C++17 + rclcpp + Qt 5.15 Quick 씬그래프 (QML 엔진 없음)**

| 후보 | 판정 |
|---|---|
| **C++ + Qt Quick 씬그래프** | **채택.** GPU 배칭, 런타임이 얇아 systemd 서비스에 적합, 팀이 이미 C++ ROS 노드를 빌드한다 |
| QML 엔진 추가 | 크롬 레이어에 편하지만 런타임 모듈 의존성과 엔진 기동 비용이 붙는다. 필요해지면 그때 얹는다 |
| Python + PyQt | 부팅 지연과 프로세스 무게만 손해. 시각 설계는 이식 가능 |
| three.js + rosbridge | 시각 반복은 빠르나 Chromium 부팅 무게 + JSON 홉 + 크래시 시 검은 화면 |
| Godot / Unity | ROS 연동 비용, 팀 경험 없음, 부팅 무게 |
| RViz 플러그인 | 개발자 도구지 사용자 화면이 아니다 |

Qt 5.15를 쓰는 것은 이 머신에 이미 있기 때문이다(Qt6는 미설치, 설치에 sudo 필요).
Qt6로 올려도 씬그래프 API는 거의 같다.

## 9. 광학 보정과 주변광 적응

**광학 보정을 호모그래피로 흡수한다.** 컴바이너 투사는 좌우 반전과 키스톤 보정이
필요하다. 지면 투영이 이미 호모그래피이므로 곱하면 된다.

```
최종 = H_광학보정 × H_가상카메라 × 지면점
```

`H_광학보정`은 런타임 파라미터(`config/display_geometry.yaml`)다. **아트에 굽지
않는다** — 하드웨어가 한 번 더 바뀌면 전부 다시 그려야 한다.

**주변광 적응.** 주간 외광 대비가 이 방식의 최대 난제다. 전역 휘도 스케일을 두되
수동 노브로 두지 않는다. **전방 카메라의 자동노출 값이 공짜 조도 센서다** — 이미
발행되고 별도 하드웨어가 필요 없다. 야간 과밝기로 눈부심을 만드는 것이 주간
흐림만큼 위험하므로 양방향으로 작동해야 한다. **미구현.**

## 10. 확정해야 할 광학 기하 — 민경태

가장 중요한 숫자는 **가상상의 화각**이다. 좁으면 "차 앞 8 m까지 펼쳐진 원근
지면"이라는 그림 자체가 성립하지 않고, 2.5D 뷰는 화면 전체를 쓰는 장면이 아니라
**중앙에 놓인 압축된 계기**가 되어야 한다.

그래서 레이아웃을 하드코딩하지 않고 표시 기하 설정에서 유도한다.

```yaml
virtual_image_fov_deg: [?, ?]   # 최우선 미확정
eye_relief_m:           ?       # 최소 획 두께의 각도 환산 기준
keystone_corners:       [...]   # 현장 캘리브레이션
mirror:                 horizontal
```

화각이 좁게 나오면 우선순위를 이렇게 접는다:
**장애물 방향·근접도 > 현재궤적 > 이상궤적 > 표지판·신호등.**

실물이 나오면 확인할 것 셋 — 이중상(웨지 필름 유무), 실제 최대 휘도,
아이박스가 머리 위치 변화를 얼마나 허용하는지.

## 11. Orin — 토폴로지 A

Orin Nano Super가 **인지와 표시를 모두** 담당한다. 5개 원시 스트림을 받아
오도메트리·점유지도를 돌리고 HUD도 그린다.

### 자원 경합이 진짜 위험이다

상위 문서가 적어놓은 것:

- *"Orin Nano Super는 6코어이고 A78AE는 이 데스크톱 코어보다 느리므로 CPU만으로는
  5 Hz 예산에 못 든다"* (17-1)
- plane sweep CUDA 외삽이 카메라 2대에 80~160 ms (17-2)
- **이 프로젝트는 Orin을 한 번도 실측한 적이 없다.**

카메라가 3대가 되고 HUD 렌더가 **같은 GPU**를 쓴다.

### 원칙

> **HUD는 예약된 예산을 갖고, 절대 자기가 먼저 양보하지 않는다.**

프레임을 버려야 하면 인지 갱신을 버리지 HUD 프레임을 버리지 않는다. HUD가
제품이고 인지는 입력이다. 7절의 최신값-전용 비차단 구조가 이것을 자동으로
보장한다 — HUD는 vsync마다 최신 상태를 그릴 뿐 인지를 기다리지 않는다.

### 네트워크 함정 — 이미 한 번 당했다

시뮬레이션 PC → Orin으로 토픽이 넘어가면 상위 문서 13-2가 그대로 재현된다.

> `net.core.rmem_max`가 212,992 바이트인데 mono8 프레임 하나가 518,400 바이트.
> 프레임이 UDP 데이터그램 수백 개로 쪼개져 오고 조각 하나만 잃어도 샘플 전체가
> 버려진다.

Jetson 기본값도 작다. 카메라 3대면 더 심하다. 증상은 "40 Hz만 도착한다"로
나타나고 특징 수를 줄여도 해상도를 줄여도 안 변해서 엉뚱한 곳을 파게 만든다.
**Orin 프로비저닝에 `rmem_max` 상향을 처음부터 넣는다.**

다행히 **HUD 프로세스 자체는 영상 토픽을 하나도 받지 않는다.** 가산광 컴바이너에
카메라 영상을 띄울 일이 없다(밝은 사각형이 전방 시야를 가린다).

### 부팅

데스크톱 환경 없이 `QT_QPA_PLATFORM=eglfs` + `eglfs_kms`로 DRM/KMS 직행.
컴포지터가 없으니 부팅이 빠르고 오버헤드가 없다. systemd 유닛에서 ROS 환경을
소싱하고 `Restart=always` + 워치독.

**부팅 진입 시간을 숫자로 목표를 잡는다.** 전원 인가 후 N초 내 대기 화면.
사용자가 "고장인가"를 판단해야 하는 검은 화면 구간을 없애는 것이 목적이다.

## 13. 프로토타입에서 나온 것 (2026-08-05)

설계만으로는 안 나왔고 띄워보고서야 나온 것들이다.

### 13-1. 후진에 시야가 없었다 — 안전 결함

기어 R에서 화면이 통째로 비었다. 현재궤적이 차 뒤로 뻗는데 가상 카메라는 앞만
보고 있었다. 5절에 "기어가 HUD의 모드 선택자다"라고 써놓고 구현하지 않은 것이다.

**빈 화면은 저시력 사용자에게 "장애물 없음"으로 읽힌다.** 3절 규칙 1이 금지하는
바로 그것을 기어 하나로 만들고 있었다. `DisplayGeometry::rear_view`를 넣어 기어 R
에서 가상 카메라를 뒤로 돌린다.

좌우는 **거울 규약**을 따른다 — 차량 좌측이 화면 좌측. 후방 카메라와 룸미러가 쓰는
규약이고 운전자의 심상과 맞는다. 여기서 부호가 뒤집히면 후진 중 조향 안내가 정확히
반대가 되므로 테스트로 고정했다(`RearViewKeepsMirrorConvention`).

시야가 뒤집혔다는 것은 반드시 화면에 표시한다("후방 시야"). 표시 없이 뒤집힌 화면은
좌우 판단을 통째로 반대로 만든다.

### 13-2. 화각 34°는 아무것도 못 읽는다 — 실측

처음 기본값 34°에서 폭 1.82 m 리본이 **3 m 앞에서 화면 폭 1280 px를 통째로 채웠다.**
궤적이 화면 밖으로 밀려나고 눈금만 사선으로 남는다. 75°로 넓히니 2.6 m부터
지평선까지가 들어오고 리본이 읽힌다.

이것이 10절의 화각 질문에 숫자를 준다. **실제 컴바이너가 이만큼 못 내면 레이아웃을
"장면"에서 "계기"로 접어야 한다**는 것이 추정이 아니라 측정이 되었다. 민경태의
숫자를 받는 즉시 이 판단을 내릴 수 있다.

### 13-3. 발행 노드가 새서 측정 두 장이 오염됐다

`pkill -x scenario_publisher`가 아무것도 죽이지 않았다. `/proc/<pid>/comm`이 15자로
잘려 `scenario_publis`가 되기 때문이다. 이전 실행의 발행 노드들이 살아남아 같은
토픽을 함께 쏘았고, "approach 시나리오"로 찍은 화면에 degraded 시나리오의 배너가
찍혔다.

`ros2 run`이 파이썬 런처라 `$!`를 죽여도 실행 파일이 고아로 남는 것도 함께 걸렸다.
`tools/shoot.sh`가 패턴으로 정리하고 **끝난 뒤 살아있는 개수를 확인**한다.

상위 문서 13-4가 이미 적어둔 함정이다: *"매 측정 전에 `stop_stack.sh`를 부르고
살아있는 개수를 확인해야 한다."* 새 워크스페이스에서 같은 실수를 다시 했다.

### 13-4. 글자는 안 읽힌다 — 측정

"저시력자에게 비친화적인 UI 아닌가, 아무리 굵어도 글자가 읽히겠나"라는 지적을 받고
`tools/acuity_sim.py`로 쟀다. 시력 0.1은 10 arcmin을 분해하고, 스넬렌 글자는 최소
세부의 5배이므로 **문턱 글자 높이가 50 arcmin ≈ 0.83도**다. 문턱은 "겨우 판별"이지
"읽힌다"가 아니어서, 흘끗 보는 과업에는 문턱의 3배를 잡아야 한다.

현재 `chrome_item.cpp`가 쓰는 크기(`h/6`, `h/12`, `h/18`)를 화각별로 대조한 결과다.

| 화각 | 픽셀당 | 권장 글자 | 기어 120px | 코칭 60px | 건강도 40px |
|---|---|---|---|---|---|
| 75° | 3.89′ | 39 px | 권장 이상 | 권장 이상 | 권장 이상 |
| 30° | 1.43′ | 105 px | 권장 이상 | **읽기 어려움** | **읽기 어려움** |
| 12° | 0.56′ | 266 px | **읽기 어려움** | **판별 불가** | **판별 불가** |

컴바이너의 현실적인 화각에서는 **화면의 글자가 전부 못 읽는다.** 지적이 맞다.

**다만 선은 예상보다 잘 버틴다.** 검은 배경 위 밝은 선은 분해 한계보다 가늘어도
"있다"는 검출이 된다(12°에서 획 5 px = 2.8 arcmin인데 궤적과 갈매기가 남는다).
무너지는 것은 **가까이 붙은 선 여럿을 여럿으로 분해하는 것**이고, 그 희생자가
1 m 간격 거리 눈금 사다리다 — 12° 시뮬에서 위쪽 눈금이 회색 띠로 뭉친다.

### 13-5. 정보 예산을 다시 세야 한다

시력 0.1에게 12° 가상상은 **72 × 41개의 분해 셀**이다. 그 사용자에게 이 화면은
사실상 72×41 픽셀 디스플레이다. 구분 가능한 표식을 5~10개쯤 놓을 수 있고,
그것이 예산의 전부다. 장면이 아니라 **아이콘**을 설계해야 하는 크기다.

| 화각 | 분해 셀 (가로 × 세로) |
|---|---|
| 75° | 450 × 256 |
| 30° | 180 × 103 |
| 12° | **72 × 41** |

### 13-6. 규칙을 써놓고 같은 세션에 어겼다

4절에 "픽셀이 아니라 시각(視角)으로 설계한다"고 적어놓고, `chrome_item.cpp`는
글자 크기를 `h / 6`, `h / 12`, `h / 18`로 정했다. 화면 높이의 분수는 시각이 아니다.
그래서 같은 코드가 화각에 따라 읽히기도 하고 안 읽히기도 하는데, 그 사실이 지적을
받기 전까지 드러나지 않았다.

**시뮬레이션의 한계도 적어둔다.** `acuity_sim.py`는 굴절성 흐림만 흉내낸다. 대비
감도 저하, 중심암점·시야결손, 주간 외광 워시아웃은 반영하지 않는다. 셋 다 상황을
나쁘게만 만들므로, **여기서 읽히더라도 실물에서 읽힌다는 보장은 없고 여기서 안
읽히면 실물에서도 안 읽힌다.** 그리고 시력 0.1이라는 숫자만으로는 병인을 알 수
없다 — 균일한 흐림인지 중심암점인지에 따라 배치 전략이 정반대가 된다.
조아영님께 확인할 항목이다.

### 13-7. 각도 예산을 1차 설정으로 올렸다

`include/hero_hud/angular.hpp` 가 규칙을 강제한다. 모든 크기는 **분해 한계의
배수**로 적히고 픽셀은 거기서 유도된다. 화각이 바뀌면 픽셀이 따라 바뀐다.

| 항목 | 배수 | 시력 0.1에서 |
|---|---|---|
| 획 두께 | 분해 한계 × 2 | 20 arcmin |
| 장애물 표식 | 분해 한계 × 12 | 2.0° |
| 글자 캡하이트 | 스넬렌 문턱 × 3 | 2.5° |
| 표식 최소 간격 | 분해 한계 × 2 | 20 arcmin |

**예산을 못 맞추면 그리지 않는다.** 12도에서 읽히는 글자는 266 px = 화면 높이의
37%라 글자를 통째로 생략하고 경고를 로그에 남긴다. 못 읽는 글자를 그리는 것은
잉크를 쓰고 시야를 가리면서 아무것도 전달하지 않는 일이다.

따라서 **저하 배너를 글자에서 도형으로 옮겼다.** 시스템 상태는 테두리가 나른다:

| 상태 | 테두리 |
|---|---|
| 정상 | 네 귀퉁이 짧은 표식 (살아있다는 증거, 빛을 거의 안 씀) |
| 대기 | 흐린 전체 테두리 |
| 인지 대기 | 앰버 전체 테두리 |
| 인지 신뢰 불가 | 붉은 굵은 테두리 + 점멸 |

점멸을 쓴 이유는 **시간 채널이 시력과 무관**하기 때문이다. 흐림을 그대로 통과한다.

같은 이유로 1 m 눈금 사다리를 폐기했다. 이제 화면에서 충분히 벌어지는 거리
(1/2/3/5/8 m 후보 중)에만 최대 세 개를 놓는다. 그리고 흐림 속에서 하나로 뭉칠
장애물 표식들은 **미리 합친다** — 따로 그려봐야 사용자에게는 하나로, 게다가 크기가
틀리게 보인다.

### 13-8. 12도에서는 지면 투시도 자체가 성립하지 않는다

각도 예산을 넣고 12도로 렌더링해 보니 **화면이 통째로 비었다.** 기하 때문이다.

화각 12도·피치 22도면 보이는 지면 띠가 **2.5 ~ 3.6 m뿐**이다. 그 거리에서 폭
1.82 m 리본의 가장자리는 좌우 ±17도이고 화면은 ±6도다. 장애물은 위로 벗어난다.
그릴 것은 다 계산되는데 전부 뷰포트 밖으로 나간다.

**빈 화면이 정상처럼 보이는 것은 3절 규칙 1을 정면으로 어긴다.** 그래서 뷰포트
안에 실제로 들어온 정점이 있는지 세고, 없으면 점멸하는 앰버 대각선 X를 띄운다 —
"이 화면은 지금 아무것도 말하지 않는다". `world.empty()` 로 물으면 안 된다는 것도
여기서 나왔다. 버퍼는 가득 차 있고 화면만 비어 있기 때문이다.

**이것이 10절의 화각 질문을 이분법으로 만든다.** 실제 컴바이너가 좁으면 지면
투시도는 폐기하고 다른 매핑으로 가야 한다. 그리고 그럴 자유가 있다 —
**장면 정합이 없으므로 투영이 물리적으로 옳을 의무가 없다.** 지금 핀홀 가상
카메라를 쓴 것은 습관이지 요구사항이 아니다. 가독성을 목적으로 한 매핑
(측방은 고정 스케일, 종방향은 압축)이면 화각과 무관하게 내용이 항상 화면을
채운다. 미착수이며, 민경태의 숫자를 받고 착수한다.

### 13-9. 10인치 패널이 화각을 사실상 확정한다

화면을 10인치로 잡는 순간 화각이 계산된다. 패널의 각크기는 광로 길이가 정하고,
평면 컴바이너면 광로 = (눈→컴바이너) + (컴바이너→패널)이다.

| 광로 | 화각 | 분해 셀 (시력 0.1) |
|---|---|---|
| 0.7 m | 17.5° | 106 × 66 |
| **1.0 m** | **12.3°** | **74 × 46** |
| 1.2 m | 10.3° | 62 × 39 |

10인치 16:10 패널은 215 × 135 mm다. **화각 미확정이 아니라 10~18° 구간으로
좁혀졌고**, 그 전 구간이 13-8이 측정한 "핀홀 투시도가 죽는" 영역이다.

그래서 `DisplayGeometry` 가 물리 사양(대각 인치·종횡비·광로)에서 화각을 유도한다.
`hfov_deg` 를 양수로 주면 그것이 이기지만 기본은 유도다.

### 13-10. 투영을 가독성 매핑으로 바꿨다

핀홀을 버렸다. 기본이 `ViewMapping::Legibility` 다.

- 횡방향: ±3 m 가 화면 폭. 먼 쪽은 `taper` 만큼 좁아져 원근처럼 읽힌다
- 종방향: 거리^0.55 로 압축. 가까운 곳이 화면을 더 많이 가져간다
- 담는 범위가 설정으로 고정이므로 **화각이 아무리 좁아도 내용이 화면을 채운다**

근거는 07-07의 "장면 정합 X"다. 겹칠 실세계가 없으므로 투영이 물리적으로 옳을
의무가 없다. 핀홀을 쓴 것은 습관이었고, 12도에서 화면이 통째로 비면서 대가를
치렀다.

### 13-11. 선에서 덩어리로 — 그리고 그 대가

"선보다 덩어리를 쓰는 게 낫지 않나"는 지적이 맞았다. 흐림은 **폭이 좁은 것의
진폭을 먼저 깎는다.** 획은 흐림 반경보다 가늘어지면 흐려지지만 덩어리는 최고휘도를
거의 그대로 지킨다. 장애물 표식을 채운 쐐기로 바꾸자 12.3도 시뮬에서 또렷해졌다.

부호화를 네 채널로 갈랐다. **색조 하나에 기대지 않는다.**

| 등급 | 색조 | 휘도 | 크기 배수 | 점멸 | 채움 | 막대 |
|---|---|---|---|---|---|---|
| Info | 흰색 | 0.40 | 1.00 | | 테두리 | |
| Caution | 앰버 | 0.75 | 1.15 | | 테두리 | |
| Warn | 적등 | 1.00 | 1.30 | | **채움** | 1개 |
| Critical | 적등 | 1.00 | 1.45 | **○** | **채움** | 2개 |

점멸은 꺼지지 않고 휘도 30%로 내려간다 — 완전히 사라지면 "없음"으로 읽힌다.
크기 배수를 작게 둔 이유는 크기가 이미 거리를 나르고 있어서다. 위협까지 크기로
부호화하면 가까운 정보성 물체와 먼 임계 물체가 같은 덩어리가 된다.

**대가를 쟀다.** 전부 채웠더니 켜진 면적이 **57~64%** 였다. 가산광에서 이것은
전방 시야를 그만큼 가린다는 뜻이다. 위험한 것(Warn 이상)만 채우고 나머지는 굵은
테두리로, 궤적 획을 2.0 → 1.5배로, 거리 띠를 셋 → 둘로 줄여 **36~43%** 가 됐다.
겹침을 중복으로 세고 화면 밖 정점도 포함하므로 이것은 상한이다.

굵은 테두리도 획이 분해 한계의 두 배라 단면으로는 여전히 덩어리이고, 속이 비어
그만큼 앞이 보인다. **덩어리는 공짜가 아니고, 어디에 쓸지가 설계다.**

### 13-12. 표식 개수에도 예산이 있다

덩어리로 바꾸고 나니 화면이 과밀해졌다. 74 × 46 셀에 장애물 다섯을 다 그리니
서로 겹쳐서 개수도 위치도 안 읽혔다. **다 그리는 것은 아무것도 안 그리는 것과
같다.**

- 동시 표식 최대 3개 (`acuity.max_marks`). 위험한 것 먼저, 같은 등급이면 가까운 것
- 합치는 문턱을 분해 한계가 아니라 **그려질 덩어리 크기**로. 겹쳐 그려지면 하나로
  보이므로 미리 합치는 편이 정직하다
- 잘라낸 것이 있으면 우측에 막대 세 개로 표시한다. 조용히 생략하면 화면이
  "이게 전부"라고 주장하게 되고, 그것은 3절 규칙 1을 어긴다
- 그리는 순서가 겹칠 때의 우선순위다. **현재궤적이 가장 위** — 인지와 무관하게
  정확한 유일한 요소이기 때문이다

### 13-13. 궤적은 선이 아니라 면이다

"덩어리로 선을 만들지 말고 궤적을 속이 찬 다각형으로" 라는 지적을 받았다. 맞다.
굵은 막대 두 줄과 가로 눈금을 그린 것은 덩어리를 **선의 재료로** 쓴 것이고,
화면은 커다란 네모들의 사다리가 됐다.

**궤적의 진짜 정체는 차가 실제로 덮을 지면이고, 그것은 면이다.** 가장자리 두 줄은
그 면의 경계일 뿐인데 경계만 그리고 있었다.

- 현재궤적: 좌우 경계 사이를 **채운 띠**. 자차가 덮을 면.
- 이상궤적: 그 위에 얹힌 **좁고 밝은 앰버 자취**. 덮을 면이 아니라 따라갈 선이므로
  성격이 다르고 폭도 다르다. 넓은 면 둘이 겹치면 어느 쪽도 안 읽힌다.
- 거리 눈금 폐기. 페이드가 그 일을 한다.

**멀수록 옅어지는 것은 장식이 아니다.** 예측 신뢰도가 거리에 따라 죽는 것을 그대로
표현한 것이다 — 1초 뒤 차가 있을 자리는 확실하고, 8 m 앞은 조향 한 번에 달라진다.
`QSGVertexColorMaterial` 의 정점 색으로 공짜로 얻는다.

**그리고 이것이 가림을 줄였다.** 켜진 면적이 **36~43% → 12~18%** 로 떨어졌다.
막대 두 줄은 전 구간이 최대 휘도였는데, 채운 띠는 대부분이 어둡고 밝은 곳은
발밑뿐이기 때문이다. 채우는 편이 오히려 쌌다.

곁들여 고친 것 둘: 위협 받침을 쐐기 밑변에 **붙였다**(띄우면 떠 있는 사각형
두 개로 보인다), 그리고 표식 앵커를 획 두께까지 포함해 화면 안으로 당겼다
(꼭짓점만 넣으면 테두리 획이 잘린다).

### 13-14. 심볼 11종을 3종으로

"해석 안 되는 심볼, 애매한 크기 균형, 가려짐, 마감이 이상한 선, 고휘도·고채도
활용성 낮음"이라는 지적을 받았다. 전부 맞았다. 자체 비판을 적어두면:

- 삼각형이 왜 장애물인지 설명할 근거가 없었다. 차인지 벽인지, 크기가 얼마인지
  아무것도 안 나오고 "위협 등급"만 그렸다. **물체를 안 그렸다.**
- 화면에서 제일 크고 밝은 것이 인지에서 온 정보였다 — 차 재현율 0.603짜리.
  CAN에서 직접 오는 유일하게 정확한 궤적은 흐린 회색 바탕이었다. 5절에 써놓은
  신뢰도 계층을 화면에서 거꾸로 그렸다.
- 경고 삼각형이 코리도 위에 얹혀 봐야 할 경로를 그 자리에서 덮었다.
- 코리도 윗변이 하드 클립으로 뚝 잘렸다. 배열이 끝나서 끝난 것이지 디자인이
  끝낸 것이 아니었다.
- 최대 휘도를 "권고"인 목표선에 썼다. "지금 멈춰"에 남겨둔 여유가 없었다.

HUD 설계 지침은 서로 다른 심볼 **4개 이하**를 권한다(최적화해도 5~6). 중심시
5도 안의 심볼 배치는 방해가 되고, 휘도 대비는 7:1이 최적이다. 제 화면은 11종이었다.

셋으로 줄였다.

| 요소 | 무엇 | 휘도 |
|---|---|---|
| 코리도 | 자차가 덮을 지면. 곡률 = 조향 | 0.30 → 0.03 (페이드) |
| **정지선** | 코리도가 끊기는 자리 | **1.0 — 화면에서 유일** |
| 목표선 | 따라갈 자취 | 0.62 → 0.12 |

**장애물을 심볼로 그리지 않는다. 갈 수 있는 거리로 말한다.** 코리도의 길이가 곧
여유거리이고, 그것이 운전자가 실제로 쓰는 정보다.

자차 실루엣은 그리지 않는다 — 코리도가 시작되는 곳이 곧 차다. 후진은 코리도
밑변을 아래로 꺾어 표시하고, 저하는 코리도를 가로 줄무늬로 짠다. **둘 다 새
심볼이 아니라 같은 도형의 마감·질감이다.**

### 13-15. 만들고 나서 눈으로 잡은 것 넷

원본과 흐림을 나란히 보지 않으면 안 나오는 것들이다. `tools/shoot.sh` 가 이제
항상 `<이름>.pair.png` 를 함께 낸다.

1. **바닥에 98 px 틈.** 코리도가 휘면 시작점의 법선이 뒤로 기울어 가장자리 한쪽의
   x 가 음수가 되고, 그 표본이 통째로 버려졌다. 발밑의 작은 음수는 0으로 붙인다.
2. **화면의 29%만 썼다.** ±3 m 를 화면 폭에 매핑하니 차폭 1.82 m 코리도가 좁은
   리본이 됐다. ±1.6 m / 6 m 로 좁혀 57%.
3. **위급할수록 화면이 작아졌다.** 길이가 곧 여유거리이므로 장애물이 가까우면
   코리도가 사라진다 — 정확히 거꾸로다. **정지선이 가까울수록 넓어지고 두꺼워지고
   빠르게 점멸**하게 했다. 0.5 m 에서는 화면 폭 전체를 가로지른다.
4. **저하 줄무늬가 흐림에서 사라졌다.** 표본 인덱스로 잘라서 원근 압축 때문에 먼
   쪽 띠가 분해 한계보다 얇아졌다. **화면 세로 기준**으로 자르고 표본을 48 → 160
   으로 올려 띠/간격이 36~45 px(분해 한계 17.3 px)로 고르게 됐다.

켜진 면적은 **9~10%** 다.

### 13-16. 목표선의 구분을 색에서 구조로

목표선은 코리도와 **색조로만** 갈리고 있었다. 앰버와 회색은 휘도까지 가까워서,
저시력에서 색 단독 인코딩 금지를 사실상 어기고 있었다.

**어두운 양옆 + 밝은 심**으로 바꿨다. 흐림을 통과하는 것은 색조가 아니라 이
국소 대비 구조다.

```
코리도 41 │ 홈 0 │ 심 55 │ 홈 0 │ 코리도 41      (화면 세로 62% 위치의 가로 단면)
   357px    40px   60px   40px    116px          분해 한계 17.3px
```

세 특징이 모두 분해 한계의 두 배 이상이라 흐림에서 홈이 그대로 남는다.

한 벌의 처리가 두 경우를 덮는 것이 이 방식의 이점이다 — 코리도 위에서는 검은
홈이 파이고, 목표선이 코리도 밖으로 벗어나면 양옆이 배경과 같은 검정이라 심만
남는다. 그리고 검정은 가산광에서 빛을 안 내므로 **홈은 켜진 면적을 늘리지 않는다.**

### 13-17. 막대를 버리고 코리도를 나눠 칠하다

"여전히 직관적이지 않다"는 지적. 원인은 **빨간 막대가 무슨 뜻인지 배울 방법이
없었다**는 것이다. 벽인지, 노면의 정지선인지, 길이 끝나는 것인지 화면만 봐서는
알 수 없다. 심볼은 배워야 읽힌다.

코리도를 자르지 않고 **둘로 나눠 칠한다.**

> **회색은 갈 수 있고, 빨강은 못 간다.**

읽는 법이 하나이고 배울 것이 없다. 그리고 셋이 한꺼번에 풀린다.

| | 이전 | 지금 |
|---|---|---|
| 의미 | 막대 하나를 해석해야 함 | 두 색의 경계가 곧 갈 수 있는 거리 |
| 위급함 | 코리도가 짧아짐(= 화면이 작아짐) | **빨간 면적이 커짐** |
| 화면 활용 | 막히면 상단이 빔 | 항상 채움 |

상태 셋이 같은 규칙의 연속으로 읽힌다 — 전부 회색(비었음) → 회색 뒤 빨강(여기까지)
→ 대부분 빨강(정지). 켜진 면적은 8.9~13.3%.

### 13-18. 콜드 리드 — 맥락 없이 처음 보는 눈으로 재다

직관성은 만든 사람이 못 잰다. 무엇을 뜻하는지 이미 알기 때문이다. 그래서 화면만
넘기고 **설명 없이** 읽게 했다 (`codex exec`, 낮은 추론 강도). "억지로 맞추지
말고 안 보이면 안 보인다고 하라"는 지시를 붙였다.

**통과한 것.** 코어 규칙이 설명 없이 읽힌다.

| 질문 | 답 |
|---|---|
| 무엇을 나타내는가 | "전방 주행 경로를 HUD로 표시" ✓ |
| 회색 / 빨강 | "주행 가능 영역" / "위험, 정지, 진입 금지" ✓ |
| 세 장면의 변화 규칙 | "빨간 영역이 내 진행 경로를 침범할수록 위험도가 높다" ✓ |
| 지금 멈춰야 하는 것 | 정확히 지목 ✓ |

**실패한 것 — 후진 표시가 통째로 잘려 있었다.** 밑변 아래로 삼각형을 덧붙였는데
밑변이 이미 화면 바닥이라 꼭짓점이 화면 밖(바닥 + 83 px)으로 나갔다. 콜드 리드는
후진을 전혀 언급하지 않았고, 나중에 찍어 맞힌 근거도 "곡선 모양"이지 내 표시가
아니었다. **13-1이 안전 결함이라고 적어놓은 바로 그것이 구현에서 죽어 있었다.**

밖으로 내밀 자리가 없으면 안으로 파야 한다. 처음엔 가운데를 팠더니 위를 향한
검은 삼각형이 남아 오히려 전진처럼 읽혔다. 양옆을 파서 **코리도 밑변이 운전자
쪽을 가리키는 화살촉**이 되게 고쳤다. 재측정에서 확신도 "중"으로 읽힌다 —
개선이지만 확정은 아니다.

**애매한 것 둘.**

- 목표선 홈은 "차선 중앙선 **또는** 따라가야 할 경로"로 읽힌다. 두 해석이 같은
  행동으로 이어지므로 치명적이지는 않으나 뜻이 하나로 좁혀지지 않는다.
- 저하 줄무늬는 "거리 단계 표시"로 오독된다. 다만 화면 전체 인상은 "앞을 제대로
  인식하지 못하거나 정보가 부족한 상태"로 맞게 읽혔다 — 줄무늬가 아니라 어두움과
  성김이 그 일을 하고 있다.

**이 방법을 워크플로에 남긴다.** 만든 사람의 판단으로 직관성을 재는 것은
"측정하고 있다고 믿은 것을 실제로는 측정하지 않고 있던" 경우가 된다.

### 13-19. 목표선은 중심선 한 줄이 아니라 가장자리 두 줄

13-18의 콜드 리드가 남긴 애매함 — 중심선 한 줄이 "차선 중앙선"으로 읽히는 것 —
은 색 문제가 아니라 **개수 문제**였다. 한 줄은 중앙선이고 두 줄은 자리다.

실차 후방카메라 가이드선이 쓰는 형태이기도 하다. 그리고 정렬 판정이 훨씬 쉬워진다:
**두 줄이 코리도의 양 가장자리에 얹혔는가**를 보면 된다. 중심 하나끼리 맞추는
것보다 어긋남이 두 배로 보인다.

바꾸면서 홈(어두운 양옆)을 걷어냈다. 한 줄일 때는 색조만으로 코리도와 갈려서
구조가 필요했지만, 두 줄이 되면 개수와 위치가 이미 갈라 준다. 그리고 홈을 두면
코리도 가장자리를 갉아먹어 **정렬됐을 때조차 목표선이 바깥에 떠 보였다** —
정렬 여부를 읽는 것이 이 요소의 유일한 일인데 그것을 방해하고 있었다.

재측정한 콜드 리드:

| 질문 | 한 줄(이전) | 두 줄(지금) |
|---|---|---|
| 회색 면 | 도로/주행 가능 영역 | "차가 지나갈 예상 주행 영역/경로" ✓ |
| 주황 | "차선 중앙선 또는 따라갈 경로. **정확한 뜻은 모르겠다**" | "좌우 기준선" ✓ |
| 둘의 관계 | (안 물었음) | "예상 궤적 대 기준. **어긋나면 조향이 기준과 다르다**" ✓ |
| 할 일 | (불명확) | **"주황 두 줄 사이 중앙으로 가도록 조향을 맞춰야 한다"** ✓ |

행동까지 나온다. 켜진 면적 10~11%.

### 13-20. 목표선은 궤적이지 차선이 아니다

"가이드라인이 trajectory인데 왜 영점이 다르고 다 직선이냐"는 지적. 둘 다 맞았고
원인은 목 발행 노드였다.

**월드 고정 선을 보내고 있었다.** `y = 0` 인 월드 직선을 매 프레임 base_link 로
옮겨 보냈으니, 그것은 차선이지 궤적이 아니다. 정지선까지 잘리면 곧은 구간만
남아 직선으로 보였다.

**원점이 다르면 비교가 성립하지 않는다.** 코리도는 자차에서 시작하는데 목표선이
딴 데서 시작하면, 둘의 어긋남이 횡오차인지 헤딩오차인지 갈리지 않는다.

목을 3차 에르미트로 바꿨다 — `(0,0,헤딩 0)` 에서 목표 자세까지. 시작 접선이
차량 진행 방향이므로 **자차 바로 앞에서는 코리도와 정확히 겹치고, 목표로 갈수록
휜다.** 어긋남이 곧 조향 오차다. 실제로는 Hybrid A* 가 이 자리에 들어간다.

계약에도 못 박았다 — `TrajectoryRibbon.points` 는 자차에서 시작해야 하고 첫
접선이 차량 진행 방향이어야 한다. 상류가 차선을 보내면 HUD가 그것을 궤적처럼
그리게 되므로, 이것은 표시가 아니라 계약의 문제다.

### 13-21. 근거리 압축이 d=0에서 발산하고 있었다

바닥 모서리가 톱니였고 코리도와 목표선의 시작점이 어긋나 보였다. 콜드 리드도
"정확히 같은 곳에서 시작하지 않는다"고 읽었다.

원인은 종방향 매핑 `t = (d / range)^0.55` 다. **d=0 에서 기울기가 무한대**라
1 cm 차이가 화면에서 20 px로 벌어진다. 곡선 경로의 가장자리는 시작점에서 x 가
밀리미터 단위로 흔들리는데, 그것이 수십 픽셀의 계단이 됐다.

근거리 바닥값을 넣어 유한 기울기로 바꿨다.

```
t = ((d + d0)^c - d0^c) / ((range + d0)^c - d0^c),   d0 = 0.30 m
```

1 cm 이동이 20 px → 3 px 이 된다. 바닥 모서리가 깨끗해지고 두 요소가 같은 자리에서
시작한다.

### 13-22. 바닥이 떠 있던 진짜 이유 — 음수를 0으로 붙이고 있었다

13-21의 근거리 바닥값으로 톱니는 없어졌는데, 시작점이 여전히 화면 바닥에서 떠
보였다. 픽셀을 찍어보니 맨 아랫줄이 실제로 비어 있었다 — 코리도가 폭 73 px 짜리
쐐기로 잘려 있고 왼쪽 가이드는 아래 15 px 가 통째로 없었다.

투영값을 직접 뽑아보니 기하는 멀쩡했다.

```
표본 0: left (-0.00047, 0.910) → (276.0, 800.00)
        right ( 0.00047,-0.910) → (1004.0, 799.86)
```

**원인은 `d < 0` 을 0으로 붙인 것이었다.** 코리도가 휘면 시작점의 법선이 뒤로
기울어 가장자리 한쪽의 x 가 밀리미터 단위로 음수가 된다. 그것을 클램프하면 여러
표본이 같은 y 로 뭉쳐 첫 사각형이 찌그러지고, 화면 바닥이 삼각형으로 잘려 나간다.

0으로 붙이는 대신 **음수 구간을 선형으로 연장**했다. 기울기는 d=0 에서의 값을
그대로 쓴다.

```
d >= 0 :  t = ((d + d0)^c - d0^c) / ((range + d0)^c - d0^c)
d <  0 :  t = (c · d0^(c-1) / denom) · d        → 화면 아래로 나간다
```

그 점들이 화면 밖으로 조금 나가므로 바닥이 온전히 덮인다. 맨 아랫줄이 764 px
연속으로 채워진다(이전 73 px).

**이 버그는 스크린샷을 봐서는 안 나왔다.** 14 px 짜리라 육안으로는 "좀 떠 보이네"
수준이고, 픽셀을 줄 단위로 찍고 나서야 쐐기 모양인 것이 드러났다. 그리고 원인은
렌더가 아니라 매핑이었다.

### 13-23. 닫힌 슬롯 — 반만 통했다

곡선 가이드 두 줄이 코리도와 크게 벌어졌을 때 콜드 리드가 **"표시 정합이 틀어진
상태"** 로 읽었다. 자유 곡선 둘은 "다른 경로"로도 "어긋난 오버레이"로도 읽힌다.
그래서 먼 쪽을 마감선으로 닫아 **자리**로 만들었다.

**절반은 통했다.** 콜드 리드가 닫힌 끝을 이렇게 읽는다:

> 한쪽 끝이 닫혀 있어서 "막힌 곳", "목표 지점", "여기까지 가라"는 느낌이 생긴다.
> 단순한 차선보다 목적지/경계처럼 보인다.

**절반은 안 통했다.** 전체 인상은 여전히 오정렬 쪽이다:

> 주황색이 회색 면 밖으로 크게 벗어나 있어서, "가야 할 목적지가 저기 있다"보다
> "표시가 잘못 정렬된 것"에 더 가깝게 보인다.

마감선은 요소의 **뜻**을 고쳤지만 **어긋남의 크기**가 만드는 인상은 못 고쳤다.
지면 위 두 도형이 크게 벌어져 있으면 그 자체가 오정렬로 읽힌다.

여기서 나온 것은 표시 문제가 아니라 제품 문제일 수 있다 — **지금 조향으로 갈 수
없는 목표를 그려 보이는 것이 맞는가.** 크게 벗어났을 때 필요한 것은 먼 자리의
그림이 아니라 "어느 쪽으로 얼마나 꺾어라"이고, 그것은 `hero_coach` 의 판단이지
렌더러의 것이 아니다. 미결.

### 13-24. 담는 범위가 슬롯을 못 담는다

옆으로 벗어난 주차 자리는 횡방향 ±2.4 m 창에 안 들어간다. 슬롯은 **정렬이 어느
정도 된 최종 접근에서만** 화면에 나타나고, 그 전에는 가이드가 화면 밖으로
흘러나간다. 범위를 넓히면 코리도가 다시 좁아지므로 맞바꿈이다.

이것도 13-8과 같은 종류의 한계다 — 자차 중심의 지면 창은 옆에 있는 것을 못 담는다.

### 13-25. 지정 스펙 반영 — 그라데이션, 선 가이드, 고정 자리 셋

사용자가 화면 구성을 직접 지정했다. 그대로 구현하고 재평가했다.

**1. 감속 그라데이션.** 하드 분할("여기부터 빨강")을 버리고 코리도 **끝에서부터
점진적으로** 붉어지게 했다. 정지선이 가까울수록 붉은 구간이 앞으로 번지고 전체
채도가 오른다. 경계 하나를 읽는 것보다 번지는 양을 보는 편이 흐림 속에서 낫다.

**2. 가이드는 선으로만.** 닫힌 슬롯(13-23)을 걷어냈다. 마감선이 오정렬 인상을
못 고쳤고, 요소만 하나 늘었다.

**3~5. 고정 자리 셋.** 상단 신호, 우측 표지판, 좌측 기어. 월드는 그 안쪽에만
그린다(`layout.zone_*`).

신호는 **세 자리를 가진 신호등 머리**로 그린다. 어느 자리가 켜졌는가가 뜻을
나르므로 색을 못 봐도 읽힌다 — 색은 보강이다. 좌·우 화살표는 상태와 독립이라
머리 밖에 붙는다.

기어는 문장이 아니라 **글자 하나**다. 12.3도에서 문장은 판별 불가이고, 아는 글자
하나를 고정 자리에서 보는 것은 읽기가 아니라 형태 인식이다. 지금 기어와 다르면
앰버(바꿔라), 같으면 회색(맞다).

**고정 자리가 저시력에 유리한 이유**는 위치가 학습되기 때문이다. 어디를 볼지
알면 무엇인지 아는 비용이 크게 준다.

### 13-26. 6번 항목에 대한 판단

사용자가 비판적으로 검토하라고 한 셋.

| 제안 | 판단 | 근거 |
|---|---|---|
| 2.5D 지면 삼각형 (가감속·전후진) | **반대** | 전후진은 코리도 밑변 화살촉과 좌측 기어가 이미 말하고, 가감속은 그라데이션이 말한다. 지면 레이어는 가장 붐비는 곳이라 중복 심볼을 더할 자리가 아니다 |
| 가이드를 채운 곡면으로 | **반대** | 지면 위 채운 면 둘이 겹치는 것이 "오정렬 오버레이" 오독의 원인이었다 (13-23) |
| 겹침에 오버레이 기법 | **찬성, 적용** | 덮으면 정렬이 "가려짐"으로만 보이고 흐림 속에서 잘 안 읽힌다. 반투명으로 섞으면 겹친 구간이 제3의 색이 되어 **정렬 자체가 색으로 읽힌다** |

### 13-27. 재평가 — 위계가 또 뒤집혔고 우선순위가 없었다

**위계.** 고정 자리를 넣으니 크롬(표지판·기어·신호)이 화면에서 제일 밝고 정작
코리도가 흐렸다. 이 화면의 주인공은 경로다. 코리도 근거리 휘도를 0.30 → 0.46 으로
올리고 크롬 흰색을 235 → 200 으로 내렸다. 담는 범위도 ±2.4 → ±1.8 m 로 좁혀
코리도가 안쪽 영역을 더 채운다.

**우선순위.** 콜드 리드가 요소 넷을 전부 맞게 읽었지만 마지막 답이 이랬다:

> 방해될 수 있다. 핵심 정보가 좌·상·우로 흩어져 있어 **한눈에 우선순위를 판단하기
> 어렵다.** 빨간불과 주차 표지가 동시에 보여 의도가 약간 혼란스럽다.

정확한 지적이다. 자리를 셋 두면 각각은 읽히지만 **무엇이 급한지**는 안 읽힌다.
급할 때는 급한 것만 남기도록 했다 — 코칭 심각도가 경고 이상이면 표지판을 지우고
신호를 낮춘다. 지금 멈춰야 하는데 주차 표지를 읽고 있을 이유가 없다. 무엇이
급한지는 상류의 판단이므로 코칭 심각도를 그대로 쓴다.

### 13-28. 칸을 없애고, 점멸을 제대로 쓰고, 표지판을 자산으로 빼다

**신호의 빈 칸을 버렸다.** 신호등 머리를 그리면 꺼진 자리 둘이 아무 정보도
나르지 않으면서 화면과 빛을 쓴다. **켜진 것 하나만** 그린다.

칸을 없애면 위치 채널이 사라지므로 **형태**로 대신한다 — 적색 팔각형, 황색
삼각형, 녹색 원. 실세계 표지 관례를 그대로 빌린 것이라 배울 것이 적고 색을 못
봐도 읽힌다.

**점멸을 의미 있게 배분했다.** 지금까지 점멸은 임계 경고 하나에만 썼는데,
그것은 채널을 놀리는 것이다. 규칙은 "**아직 끝나지 않은 것이 깜빡인다**"로 잡았다.

| 대상 | 점멸 | 이유 |
|---|---|---|
| 황색 신호 | ○ | "곧 바뀐다"는 과도 상태다 |
| 기어 지시 (현재와 다름) | ○ | 아직 하지 않은 행동이다 |
| 기어 지시 (현재와 같음) | ✗ | 확인일 뿐이다 |
| 적·녹 신호 | ✗ | 정상 상태다 |
| 임계 코리도 | ○ | 기존 |

**표지판을 SVG 자산으로 뺐다.** `share/hero_hud/signs/*.svg` 를 읽어
고대비 단색 잉크로 바꿔 크게 띄운다.

변환은 원본을 가리지 않는다 — 알파에 휘도 커브(smoothstep 0.30~0.70)를 곱한다.
흰 선화는 그대로 살아남고, 실제 컬러 표지판은 밝은 부분(글자·화살표)만 남고
바탕(적색·청색 판)은 죽는다. 가산광에서 필요한 것이 정확히 그것이다.

**자산은 직접 작성했다.** 위키미디어에서 받는 것도 검토했지만 파일마다 라이선스를
확인해야 하고, 지금 필요한 다섯 종은 선화로 그리면 되는 것들이다. 파이프라인은
어떤 SVG든 받으므로 **공식 표지판 SVG 를 같은 디렉터리에 넣으면 코드를 안 고치고
바뀐다.**

**가이드 바닥 틈 (세 번째).** 목표선의 첫 표본은 자차 위치라 바닥에 정확히 앉는데,
가장자리 오프셋을 두 번 거치면(중심선 → 차폭 가장자리 → 선 두께) 첫 사각형이
바닥 모서리에 걸쳐 **왼쪽 줄 아래 20 px 가 빠졌다**. 오른쪽은 멀쩡해서 육안으로는
잘 안 보였다. 시작점을 뒤로 0.45 m 연장해 걸침을 없앴다.

같은 자리를 세 번 고쳤다(13-21 발산, 13-22 클램프, 여기 오프셋 걸침). 매번 원인이
달랐고, 매번 픽셀을 줄 단위로 찍고 나서야 드러났다. **화면 바닥은 이 설계에서
가장 예민한 자리다** — 자차가 있는 곳이고, 매핑의 특이점이 있는 곳이다.

### 13-29. 시뮬이 가장 쉬운 조건만 재고 있었다

"블러는 이 정도만 해서 보는 게 과연 맞을까?"라는 지적. 아니었다. 셋이 빠져 있었다.

**1. 흐림이 낙관적이었다.** MAR 10 arcmin 을 FWHM 으로 잡아 σ 4.25 arcmin 을 썼는데,
이는 차단 약 4.8 cyc/deg 에 해당한다. 저시력의 대비감도 차단은 보통 3 cyc/deg
이하이고 그때 σ 는 6.83 arcmin 이다. **60% 덜 흐리게 보고 있었다.**

**2. 대비감도 저하를 아예 안 넣었다.** 시력 저하보다 대비감도 저하가 지배적인
경우가 많고, HUD 는 대비가 전부인 장치다.

**3. 배경이 검정이었다 — 이것이 제일 크다.** 가산광 컴바이너는 실세계 위에 빛을
**더한다.** 검은 배경은 가장 쉬운 조건이고, 이 프로젝트의 모든 시각 판단이
거기서 내려졌다.

모형을 물리 순서로 다시 세웠다: **합성(가산) → 흐림 → 대비감도.**

### 13-30. 재측정 — 코리도는 버티고 크롬이 먼저 죽는다

맑은 낮(배경 평균 203), 시력 0.1, 차단 3 cyc/deg 기준 Weber 대비.

| 요소 | Weber 대비 | 판정 |
|---|---|---|
| 코리도 근거리 | **47.9%** | 여유 있음 |
| 가이드선 | **25.4%** | 통과 |
| 신호 (녹) | **6.4%** | **문턱 미달** |
| 표지판 획 | **0.4%** | **사실상 안 보임** |

저시력의 대비 문턱은 흔히 10~20% 다(정상은 1~2%).

**원인이 구조적이다.**

- 크롬 자리를 화면 **위쪽**에 뒀는데, 실세계에서 그 자리는 하늘이라 가장 밝다.
  **가장 어두운 요소를 가장 밝은 배경 위에 올려놨다.**
- 가산광은 더하기만 되므로 밝은 배경에서는 금세 포화한다. 255 로 잘리면 그 위로는
  대비를 더 못 만든다.
- 그리고 크롬 흰색을 235 → 200 으로 내린 것(13-27)은 **검은 배경에서 위계를
  맞춘 판단**이었다. 실제 배경에서는 그 순서가 다르게 나온다.

**주변광 적응은 선택이 아니라 필수다.** 9절에 "미구현"으로 적어둔 것이 여기서
치명적인 것으로 드러났다. 전방 카메라 자동노출을 조도 프록시로 쓰는 계획은
그대로이고, 우선순위가 바뀌었다.

`tools/shoot.sh` 는 이제 기본을 **흐린 날**로 잡고 **맑은 낮**을 따로 낸다
(`<이름>.day.png`). 검은 배경으로 시각 판단을 내리지 않기 위해서다.

**여전히 안 들어간 것**: 중심암점·시야결손(병인 미확인), 눈부심 산란, 컴바이너의
실제 최대 휘도와 투과율. 셋 다 상황을 나쁘게만 만든다. 그리고 배경은 합성이다 —
CARLA 프레임이나 실차 영상이 생기면 `--bg <파일>` 로 바꾸는 편이 낫다.

### 13-31. 주변광 적응 — 야간은 풀렸고 주간은 우리 문제가 아니었다

`/hero/ambient` 를 CAN 과 같은 계층으로 넣었다. `hero_coach` 를 경유하지 않고
HUD 가 직접 구독한다 — 인지가 죽어도 화면은 보여야 하기 때문이다.
**신호가 없으면 밝은 쪽으로 가정한다**(`ambient.assumed`): 어둡게 잡았다가 안
보이는 것이 밝게 잡았다가 눈부신 것보다 나쁘다.

```
L' = (floor + (1 - floor) * L) * gain
floor  밝을수록 올라간다 (낮은 단계가 배경에 묻히지 않게)
gain   어두울수록 내려간다 (야간 눈부심)
```

**야간은 풀렸다.** 패널 출력이 코리도 109 → 57, 신호 159 → 80 으로 내려간다.

**주간은 안 올랐다.** 출력은 109 → 152 로 올라가는데 Weber 대비가 그대로다.
합성이 255 에서 잘리기 때문이다 — 152 + 배경 172 = 324 → 255. 더 낸 빛이 버려진다.

즉 **주간 가독성의 한계는 우리 게인이 아니라 패널 최대 휘도 대 배경 휘도다.**

| 배경 | 투과율 100% | 70% | 50% |
|---|---|---|---|
| 하늘(위) 239 | **7%** | 52% | 113% |
| 중간 200 | 28% | 82% | 155% |
| 노면(아래) 165 | 55% | 121% | 209% |

가산광의 주간 상한은 `(패널최대 − 배경) / 배경` 이고 게인과 무관하다. 지렛대는
둘뿐이다 — **패널 최대 휘도**와 **컴바이너 투과율**. 둘 다 하드웨어 사양이므로
민경태에게 넘어간다. 양산 HUD 가 투과율을 낮추는 이유가 이것이다.

**그리고 배치가 하드웨어만큼 크다.** 밝은 배경 위에는 무엇을 놓아도 안 보인다.
지금 상단(신호)이 가장 나쁜 자리다.

다만 이 결론은 **합성 배경이 "위가 하늘"이라고 가정한 것에 걸려 있다.** 컴바이너를
낮게 달면 배경이 대부분 보닛과 근거리 노면이라 더 어둡고 고르다. 그러면 상단이
나쁜 자리가 아니다. 마운트 기하와 실제 배경 사진이 있어야 판정된다 — 지금은
`--bg <파일>` 로 넣을 수 있게만 해뒀다.

### 13-32. 배치 재구성 — 인셋을 버리고, 위계를 세 번 고쳤다

**인셋을 버렸다.** 고정 자리만큼 월드를 안쪽으로 밀었는데, 코리도는 원래 가운데
절반만 쓴다 — 좌우 각 25%는 **자동으로 비어 있다.**

| 거리 | 코리도가 차지하는 폭 |
|---|---|
| 바닥 | 51% (x 316~964) |
| 중간 | 42% |
| 먼 끝 | 33% |

공짜로 얻을 자리를 돈 주고 샀고, 그 대가로 코리도가 64% 폭에 갇혔다. 인셋을
없애니 코리도가 화면 전체를 쓰고 크롬은 그 여백에 산다.

**의미를 세로 위치에 대응시켰다.** 위는 앞(신호), 옆은 맥락(표지판), 아래는
지금·여기(기어). 그리고 **코너로 흩뿌리지 않는다** — 12.3도에서는 화면 전체가
거의 중심시 안이고, 저시력은 유효 시야가 더 좁아 코너를 보려면 도약안구운동이
필요하다.

### 13-33. 위계를 세 번 고쳤다 — 매번 콜드 리드가 잡았다

"가장 중요해 보이는 요소는 무엇인가"를 물으면 세 번 다 **틀린 것**이 나왔다.

**1차 — 녹색 원.** 상단 중앙에 단독으로 뜬 채도 높은 녹색 원이 화면을 지배했다.
가장 안 중요한 요소에 팔레트에서 가장 센 색을 준 셈이었다.

> 초록 원이 가장 눈에 띄지만, 실제로 중요한 것이 도로 경로인지 P인지 초록 원인지
> 바로 판단하기 어렵다.

→ **녹색을 안 그린다.** 주차 기동 중 "진행해도 된다"는 정보가 아니다. 규칙을
**"행동을 요구할 때만 뜬다"** 로 세웠다. 적·황은 뜨고 녹은 안 뜬다.

**2차 — P 표지판.** 녹색을 지우니 이번엔 표지판이 1위가 됐다.

→ 문제가 옮겨간 것이 아니라 **근본 원인이 드러났다.** 코리도는 부드러운
그라데이션이라 지각적으로 약하고, 크롬은 **경계가 뚜렷한 물체**라 강하다.
경계가 있는 작은 물체는 큰 확산 영역보다 시선을 먼저 끈다.

→ **코리도에 윤곽을 줬다.** 가장자리를 두 배 휘도의 얇은 띠로 두르면 코리도도
경계 있는 물체가 된다. 면적을 거의 안 쓰면서 지각 무게만 올리는 값싼 수단이다.
그리고 표지판을 한 단계 낮췄다 — 맥락은 경로보다 위일 수 없다.

**3차 — 통과.**

> 가장 중요해 보이는 요소는 중앙의 큰 경로 형태와 노란 경로 표시다.
> 오른쪽의 P 아이콘은 상대적으로 **보조 정보처럼 보인다.**

**교훈.** 위계는 휘도만으로 안 선다. **경계의 유무가 휘도만큼 크다.** 그리고
"어느 요소가 가장 중요해 보이나"는 만든 사람이 절대 못 재는 종류의 질문이다 —
무엇이 중요한지 이미 알고 보기 때문이다.

켜진 면적 13~21% (윤곽과 큰 코리도의 대가).

### 13-34. 데이터 통신 — 스트림마다 성격이 다르다

세 스트림을 한 QoS 로 묶고 있었다. 성격이 전부 다르므로 갈라야 한다.

| 스트림 | 주기 | 신뢰성 | 지속성 | 깊이 | 근거 |
|---|---|---|---|---|---|
| `/hero/vehicle_state` | 50 Hz | best_effort | volatile | 1 | 최신값만. **늦은 조향각은 틀린 조향각이다** |
| `/hero/scene_overlay` | 20 Hz | best_effort | volatile | 1 | 한 프레임 = 한 메시지. 쌓이면 오래된 것이 그려진다 |
| `/hero/ambient` | 2 Hz | **reliable** | **transient_local** | 1 | 아래 |

**주변광만 다르다.** 초당 두 번 바뀌는 값이라 대역폭이 문제가 아니고, **늦게 뜬
HUD 가 즉시 마지막 값을 받아야 한다.** transient_local 이 그 일을 한다 — 없으면
부팅 직후 최대 0.5초 동안 가정값(밝음)으로 돌고, 야간이면 그 사이 눈이 부신다.
가정값은 안전한 기본이지 정답이 아니다.

**표시 계층은 대역폭이 사실상 공짜다.**

```
scene_overlay   약 872 B x 20 Hz = 17.0 KB/s
vehicle_state   약  48 B x 50 Hz =  2.3 KB/s
ambient         약  40 B x  2 Hz =  0.1 KB/s
                                   ─────────
                                   약 20 KB/s

참고: 카메라 1대 raw 960x540 = 1.5 MB x 60 Hz = 89 MB/s
```

**이것이 `hero_coach` 를 두는 진짜 이유다.** 무거운 인지 출력(점유격자, 원시 검출)은
`hero_coach` 안에서 끝나고 HUD 로는 1 KB 짜리 한 장만 건너간다. 4,500배 차이다.
덕분에 표시를 다른 보드로 떼어내는 것도 선택지로 남는다.

**영상은 프로세스 경계를 넘기지 않는다.** 토폴로지 A 에서 인지와 HUD 가 같은
Orin 에 있으면 컴포저블 노드로 묶어 **직렬화 자체를 없애는** 편이 맞다. 루프백
DDS 로 89 MB/s 를 왕복시키는 것은 순전한 낭비다.

시뮬레이션 PC → Orin 으로 영상이 넘어가는 구성에서만
`config/cyclonedds.xml` 이 필요하다. 커널도 같이 올려야 한다 —
XML 만으로는 안 된다.

```
sudo sysctl -w net.core.rmem_max=16777216
```

**시각(時刻)은 두 종류를 구분해 쓴다.** 메시지 스탬프는 기록·재생용으로 채우되,
**저하 판정은 monotonic 수신 시각**으로 한다. 시뮬레이션 시각으로 재면 시뮬이
멈췄을 때 영원히 신선해 보인다.

**부재의 의미를 스트림마다 정의했다.** 이것이 통신 설계의 절반이다.

| 없을 때 | 결과 |
|---|---|
| vehicle_state | `Waiting` — 정적 프레임. 검은 화면 금지 |
| scene_overlay | `Basic` — 코리도만, 줄무늬 질감 |
| ambient | 밝은 쪽으로 가정 (`ambient.assumed`) |

### 13-35. 물리 배선 — 무엇을 어느 포트로

#### 시뮬 PC ↔ 젯슨 : 1 GbE 직결

**원본 그대로는 안 들어간다.**

| 구성 | 대역폭 | 1 GbE |
|---|---|---|
| RGB 960×540 @60 × 3대 | 280 MB/s = **2.24 Gbps** | 초과 |
| RGB 960×540 @60 × 2 + @10 × 1 | 202 MB/s = 1.62 Gbps | 초과 |
| **mono8 640×360 @60 × 2 + RGB 960×540 @10 × 1** | **43 MB/s = 0.35 Gbps** | **37%** |

**해법은 링크가 아니라 발행 내용이다.** 오도메트리 전단은 이미 mono8 640×360 만
쓰고(상위 문서 13-1), 세 번째 카메라는 표지판·신호용이라 10 Hz 면 충분하다.
소비자가 실제로 쓰는 형식으로 발행하면 6.5배가 줄고 1 GbE 에 여유가 생긴다.
색은 세 번째 카메라만 필요하다 — 신호등 색을 읽어야 하니까.

배선과 설정:

- **스위치·공유기 없이 직결.** 탐색 지연과 변동을 없앤다. 고정 IP.
- **MTU 9000 (점보 프레임).** 조각 하나만 잃어도 프레임 전체가 버려지므로
  조각 수를 줄이는 것이 곧 손실률을 줄이는 것이다.

| 프레임 | MTU 1500 | MTU 9000 |
|---|---|---|
| mono8 640×360 | 165 조각 | **26 조각** |
| RGB 960×540 | 1111 조각 | 175 조각 |

- `net.core.rmem_max=16777216` + `config/cyclonedds.xml`. 13-2 의 함정이다.
- `ROS_DOMAIN_ID` 를 고정한다. RTPS 는 도메인에서 포트를 계산한다 —
  도메인 d 는 UDP `7400 + 250·d` 부터 약 100 포트를 쓴다. 실차와 시뮬을 같은
  망에서 돌리면 도메인을 갈라야 섞이지 않는다.

#### 실차 카메라 → 젯슨 : 전·후방 CSI, 광각 USB3

- **전·후방은 CSI(MIPI).** 60 Hz 저지연이 필요하고, CSI 프레임은 GPU 접근
  가능한 버퍼로 들어와 C++ 전단이 복사를 피할 수 있다. USB 는 컨트롤러 대역을
  나눠 쓰고 지연이 더 크다.
- **광각은 USB3 로 충분하다.** 10 Hz 컬러라 대역이 남고, CSI 커넥터 수를
  아낀다 (Orin Nano 개발키트는 22핀 CSI 가 둘이다 — **보드별로 확인 필요**).
- GMSL2 는 양산이 쓰는 방식이지만 전용 캐리어 보드가 필요하다. 이 규모에서는 과하다.

#### CAN → 젯슨 : 절연 USB-CAN, **수신 전용**

- 40핀 헤더의 네이티브 CAN 은 TTL 레벨이라 외부 트랜시버가 필요하다.
  **절연형 USB-CAN 어댑터**를 권한다 — 납땜이 없고, SocketCAN 으로 바로 잡히고,
  무엇보다 **갈바닉 절연이 차량 전기계 과도로부터 젯슨을 보호한다.**
- **listen-only 모드로 연다.** 이 시스템은 코칭 전용이고 제어 개입이 없다.
  수신 전용으로 열면 소프트웨어 버그가 있어도 차량 버스에 프레임을 넣을 수
  없다 — 규칙이 아니라 물리로 보장된다.
- `can0` → `ros2_socketcan` → `hero_can_adapter` → `/hero/vehicle_state`.

#### 디스플레이 : DisplayPort

10인치 패널은 DP 또는 HDMI 입력이 있는 것으로 고른다. 원시 LVDS·MIPI-DSI 패널은
브리지 보드가 필요하니 피한다. `eglfs_kms` 가 DP 를 직접 잡는다.

#### 요약

```
        [시뮬 PC] ──1 GbE 직결, MTU 9000, 고정 도메인── [Orin Nano]
                     mono8 640x360 x2 + RGB @10 x1          │
                                                            ├─ CSI  ×2  전·후방 카메라
        [차량 CAN] ──절연 USB-CAN (수신 전용)────────────────┤
                                                            ├─ USB3      광각 카메라
                                                            └─ DP        10" 패널
```

시뮬 링크는 개발 중에만 쓴다. 실차에서는 카메라·CAN·패널만 남고 이더넷은 빠진다.

### 13-37. 후진 신호 — 화살촉이 세 번 틀렸고, 정작 기어가 없었다 (2026-08-10)

영상을 찍고 나서야 보였다. 정지 캡처로는 이 절의 어느 것도 안 잡혔다.

**화살촉의 두 결함.** 검정 삼각형으로 코리도 밑변 양옆을 파내던 방식이 동시에
둘로 틀렸다. (1) 파낸 삼각형이 **화면축에 정렬**됐다 — 코리도 근단은 조향에
따라 기울고 휘는 선인데 수직 변으로 잘라내니 꼭짓점이 중심선에서 벗어나고 좌우
빗변 각도가 달라졌다. 화살촉이 아니라 찌그러진 마름모였다. (2) **테두리가
따라오지 않았다** — 테두리는 경로에서 생성되는데 검정이 그 위를 덮으니 빗변만
불이 꺼졌다. 밝은 띠가 잘린 자리에서 뚝 끊겨, 화살표가 아니라 코리도가 파손된
것으로 읽혔다.

**고친 방법.** 검정으로 덮는 것을 걷어내고 **월드 좌표에서 근단 폭을 좁혔다.**
중심선을 향해 대칭으로 모이므로 조향과 무관하게 정렬되고, 테두리가 좁아진
모서리에서 그대로 생성되므로 빗변이 저절로 켜진다. 결함 둘이 원인 하나로
사라진다.

**그래도 흐림에서 사라졌다.** 첫 시도는 길이를 0.40 m 로 잡았는데 깊이가 90 px
였고, 심볼 문턱(분해 한계 × 6 = 104 px)에 못 미쳐 시력 0.1 에서 모서리가
둥글려져 그냥 뭉툭한 밑변이 됐다. **화살촉이 심볼로 읽히려면 심볼 크기여야
한다.** 깊이를 예산에서 가져와(문턱 × 1.6) 다시 잡으니 흐림에서도 수렴하는
쐐기로 남는다. 근단을 그만큼 먹는 것이 대가이고, 근단은 자차에 가장 가까운
구간이라 이 대가는 싸지 않다.

**정작 더 큰 것은 기어였다.** 좌측 기어가 `advised_gear` 에만 걸려 있어서 코치가
권고하는 동안(11.5~14 s)에만 떴고, **정작 후진하는 동안(14~19 s)에는 아무것도
뜨지 않았다.** 화살촉이 흐림에서 사라지는 것과 겹쳐, 시력 0.1 사용자에게는
시야가 뒤집혔다는 신호가 화면에서 완전히 사라진 상태였다. 코드 주석이 걱정하던
바로 그 상황이다.

기어는 CAN 이 주는 사실이다. 인지 계층에 묶은 것 자체가 5절의 두 계층 구조에
어긋난다 — 인지가 죽으면 기어까지 같이 죽는다. 지금 기어를 상시 표시하고,
권고가 있고 그것이 지금 기어와 다를 때만 앰버로 점멸한다. 권고는 `Normal`
에서만 받는다 — `Basic` 은 장면이 낡았다는 뜻이고 `Untrusted` 는 상류가 못
믿겠다고 말한 상태라, 둘 다에서 낡은 권고를 점멸시키면 지금 해야 할 행동인
것처럼 읽힌다.

**정지 캡처의 한계.** 이 셋 중 어느 것도 캡처로는 안 잡혔다. 화살촉의 비대칭은
조향이 큰 프레임에서만 드러나고, 기어 누락은 권고 구간 밖에서만 드러난다.
`tools/record.sh` 를 만든 이유가 이것이고, 만들자마자 값을 했다.

**캡처 대본도 이때 고쳤다.** `shoot.sh` 는 발행 노드를 먼저 띄우고 HUD 를 나중에
띄우므로 장면 시각이 1.5~2.5 s 밀린다. 지연을 손으로 맞추면 원하는 상태가 안
잡히고, 실제로 `yellow` 가 적색으로 `gear` 가 전환 후로 잡혔다. 이제 문서용
정지 컷은 **한 번의 기록에서 골라낸다** (`KEEP_FRAMES=<dir> tools/record.sh`).
무손실이고 프레임 번호가 곧 시각이다.

### 13-38. 코리도 점멸을 밝기에서 색으로 (2026-08-10)

임계 코리도는 붉은 구간의 **휘도를 0.6배로 떨궈** 점멸했다. 가산광에서 이것은
방향이 반대다 — 어두워지는 국면마다 배경 대비가 같이 떨어져 **경고가 가장
급할 때 가장 안 보인다.** 밝은 배경일수록 심해진다. 9절이 대비 상한을
`(패널최대 − 배경) / 배경` 이라고 적어놓았는데, 밝기 점멸은 그 분자를 스스로
깎는 짓이다.

적색과 백색을 번갈아 띄우는 것으로 바꿨다. 렌더 실측:

| 국면 | RGB | 시감 휘도 Y |
|---|---|---|
| 적색 | (162, 46, 15) | 68.4 |
| 백색 | (162, 162, 162) | 162.4 |

R 채널 구동은 **양쪽이 같다**(162). 백색 국면은 적색에서 밝기를 뺀 것이 아니라
G·B 를 더한 것이다. 그래서 어느 국면도 이전보다 어둡지 않고, 색과 휘도가 동시에
2.4배로 흔들린다. 휘도 증폭은 붉은 국면인지가 아니라 **위험도**에 묶어야 한다 —
흰 국면에서 같이 내려가면 결국 밝기 점멸로 되돌아간다.

**대가 둘.**

첫째, 흰 국면에서 **감속 그라데이션이 사라진다.** 코리도가 균일한 백색이 되어
"얼마나 감속해야 하는가"가 그 동안 안 보인다. 임계에서는 메시지가 이미 점진적
감속이 아니라 정지이므로 받아들일 만하다고 봤지만, 판단이지 측정이 아니다.

둘째, 흰 국면이 **정상 코리도와 같아 보인다.** 그 순간에 흘끗 보면 "비어 있다"로
읽힐 수 있다(`docs/screens/` 색인의 t=5 s 프레임이 그 상태다). 상단 적색 신호가
두 국면 모두에 계속 떠 있어 이것을 막는다 — 즉 이 설계는 **신호 인디케이터가
살아 있다는 전제에 기대고 있다.** 인지가 죽으면 신호도 같이 죽는데, 그때는
코리도도 저하 상태(줄무늬)로 가므로 임계 점멸 자체가 없다. 성립하지만 얇다.

### 13-39. 정지선을 그리고, 선을 화면 두께로, 점멸 리듬을 고쳤다 (2026-08-10)

**교대의 한쪽이 기본 코리도가 아니었다.** 13-38 에서 색만 빼고 밝기는 위험도에
묶어 두었는데, 그 결과 흰 국면이 **정상 코리도보다 밝은 흰 슬래브**가 됐다.
정상 상태와도 다르고 그라데이션도 아닌 제3의 모습이다. 두 국면은 "평소의
코리도"와 "붉어진 코리도"여야 한다. 붉은 양을 색과 밝기 양쪽에서 같이 빼도록
되돌렸다.

**점멸 리듬이 불규칙했다.** `blinkOn` 의 위상은 `fmod(now, period)` 인데 `now` 는
부팅 후 경과초(수만 초)다. 임계 코리도만 `period = 0.9 − 0.45·urgency` 로 주기를
**연속 변조**하고 있었고, urgency 가 조금만 움직여도 나머지가 통째로 튀었다.
실측하니 1프레임 켜졌다 4프레임 꺼졌다 하는 깜빡임이었다 — 경고가 아니라 고장으로
읽힌다. 주기를 상수(0.55 s)로 바꾸니 6/5 프레임으로 규칙적이 됐다. 급한 정도는
붉은 구간이 번지는 양이 이미 나른다.

**정지선을 그린다.** 그라데이션은 "얼마나 급한가"는 전해도 "어디까지"가 안
나온다 — 번지는 양은 읽어도 경계가 없어 정지 지점이 흐릿하다. 막힘 지점에
가로선 하나를 찍는다. 두 국면 모두에서 보이도록 코리도(fade 0.46)보다 밝게
(1.0) 둔다. **상류가 막힘을 모르면 그리지 않는다.**

**선의 두께를 화면에서 준다.** 목표선은 월드에서 0.18 m 폭으로 그리고 있었다.
원근 압축 때문에 가까운 쪽은 쐐기처럼 두껍고 먼 쪽은 분해 한계 아래로 얇아져,
선이 아니라 코리도 위에 얹힌 삼각형으로 보였다. 각도 예산이 획 두께를 분해
한계의 2배로 정해 놓았으므로 그 값을 전 구간에 쓴다(`addScreenRibbon`).
끝은 알파로 빼서 마감한다 — 뭉툭하게 잘린 끝은 "여기서 끝난다"가 아니라
"그리다 말았다"로 읽히고, 목표선은 코리도 한가운데서 끝나므로 특히 그렇다.

**채움과 선이 어긋나 보이던 것은 앨리어싱이었다.** 코리도는 채움과 테두리를
따로 그린 두 개의 삼각형 띠이고, 둘이 맞닿는 경계가 이 화면에서 가장 긴 선이다.
다중샘플링이 없어 그 경계가 표본마다 계단으로 튀었다 — 실제로 어긋난 것이
아니라 같은 곡선을 두 번 래스터화한 결과다. `QSurfaceFormat::setSamples(4)`.

**되살아난 문제.** 목표선이 화면 두께를 갖게 되면서 우측 목표선이 표지판 자리
위를 지난다. 크롬과 월드가 겹치는 문제가 다른 경로로 돌아왔다. 14절에 되돌려
적는다.

### 13-40. 정지 녹색, 거리 눈금, 정지선을 팔레트에 맞춤 (2026-08-10)

**정지선 색을 코리도에 맞췄다.** 백색으로 고정했던 판은 붉은 구간 한가운데에
팔레트 밖의 흰 막대가 얹혀 다른 계통의 표식으로 보였다. 그 자리의 코리도 색조를
쓰되 밝기만 1.0 으로 올린다 — 코리도는 fade(근단 0.46)를 쓰므로 두 국면 모두에서
위로 뜬다.

**정지선 두께가 2.5D 를 따른다.** 지면 위의 것이므로 거리에 따라 줄어야 한다.
화면 고정 두께로 그리면 먼 정지선이 가까운 것과 같은 굵기가 되어, 지면에 놓인
선이 아니라 화면에 붙은 막대로 보인다. 목표선이 반대인 이유는 그쪽이 깊이
방향으로 뻗는 선이기 때문이다. 다만 획 두께의 0.6배를 바닥으로 두고 그 아래로는
넓혀 붙잡는다 — 원근을 따르되 안 보이는 것보다는 낫다.

**정지 상태에서 코리도가 녹색이 된다.** 속도 0.08 m/s 미만. 이것은 "가도 좋다"가
아니라 **"지금 멈춰 있다"**는 상태 표시다. 주차는 정지 → 기어 변경 → 재출발의
반복이고, 속도를 숫자로 읽을 수 없는 화면에서 "지금 서 있는 게 맞나"의 확인을
바탕색이 대신한다. 막혀 있으면 먼 쪽은 그대로 붉다 — 근단 녹색 + 원단 적색은
"너는 멈췄고, 앞은 여전히 막혀 있다"로 둘 다 참이고, 정지했다고 장애물이
사라지지 않으므로 붉은 쪽을 지우면 안 된다.

녹색은 4절이 배제한 청색과 반대로 시감 효율이 가장 높다. 실측하니 녹색 코리도는
백색보다 **오히려 어둡다**(Y 93 대 116, 켜진 면적은 같음). 채도 때문에 강해
보이지만 휘도는 낮으므로, 행동을 요구하지 않는 상태색으로 적절하다 — 녹색 신호를
억제한 원칙(13-33)과도 충돌하지 않는다.

**거리 눈금을 더했다.** 자차에서 0.3 / 0.6 / 1.0 m. 정지선이 *상류가 무엇을
봤는가*라면 이쪽은 *기하*이고, 인지가 죽어도 남는다 — 저하 상태에서 화면에 남는
유일한 거리 정보다. 줄무늬 코리도가 "무엇이 있는지 모른다"고 말하는 동안에도
"이만큼이 얼마인지"는 여전히 참이므로, `textured` 여부와 무관하게 그린다.

처음에는 코리도를 가로지르는 막대로 그렸는데 **저하 상태의 줄무늬와 같은 시각
언어**가 됐다. 실측하니 근거리에서 막대 31~37 px 에 간격 31~35 px 로, 듀티가
거의 50% 라 구별이 불가능했다. 각도 예산이 획 두께와 최소 간격을 둘 다 분해
한계의 2배로 잡으므로, 근거리에 눈금 셋을 가로로 놓으면 **반드시** 줄무늬가
된다 — 피할 수 없는 충돌이다. 양 끝에서 26% 만 들어오는 눈금으로 바꿨다.

### 13-41. 수평선의 마감 — 색을 코리도에서 만들고, 두께를 거리에서 잡는다 (2026-08-10)

**색.** 정지선과 거리 눈금을 고정 색으로 칠하고 있었다(각각 밝기 1.0, 0.72).
코리도는 세로로 페이드되는데 막대만 평평하니, 지면에 놓인 선이 아니라 위에
붙인 스티커로 보였다. 색을 **그 자리의 코리도에서 만든다** — 테두리가 이미
쓰는 방식(코리도 색 × 2)을 그대로 쓰고, 눈금은 배율만 낮춘다(× 1.55).
그러면 백/녹/적 어느 국면에서도 자동으로 같은 계통이 되고, 점멸 중에도 따로
논 적이 없다.

**마감 — 두 번 틀렸다.** 첫 판은 단색 사각형이라 코리도의 세로 페이드 위에서
막대만 평평했다. 두 번째 판은 가운데를 밝게 양끝을 어둡게 하는 **밝기 범프**를
넣었는데, 그것은 코리도와 무관한 인공적인 굴곡이라 표면에 새긴 자국이 아니라
도장(엠보싱)처럼 보였다. **그라데이션을 만들어 넣는 것이 문제였다.**

답은 만드는 것이 아니라 **가져오는 것**이다. 막대를 다섯 단면으로 자르고 각
단면에 **그 호길이의 코리도 색**을 그대로 준다(배율만 올림). 막대 안의 색 변화가
코리도 자신의 그라데이션이 되므로, 백·녹·적 어느 국면에서도 그리고 붉어지는
중간에서도 따로 놀지 않는다. 테두리가 이미 쓰던 어법이고, 처음부터 거기 답이
있었다.

**두께.** 표본 인덱스로 잡고 있었다. 정수로 양자화되는 데다 화면 하한까지
걸리니 눈금마다 두께가 제멋대로였다 — 실측 23 / 31 / 37 px 였고, **가까운
눈금이 오히려 얇아 원근이 뒤집혀 있었다.** 경로 위 정확한 호길이에서 잘라
보간하고, 하한도 정수 표본이 아니라 연속으로 키운다. 다시 재니 19 / 21 / 25 px
로 가까울수록 두꺼워지고 계단이 없다.

**눈금이 테두리를 갉아먹고 있었다.** 코리도 가장자리에서 시작하게 두었더니
테두리(코리도 색 × 2) 위를 눈금(× 1.55)이 덮어, 화면에서 가장 밝은 선에 눈금마다
흐린 홈이 파였다. 테두리는 코리도를 "경계가 있는 물체"로 만들어 위계를 잡는
요소이므로(13-32), 그 연속성을 끊는 것이 눈금을 얻는 것보다 손해다. 테두리 반폭
만큼 안쪽에서 시작하게 하니 난간에 붙은 눈금자로 읽히고 테두리는 그대로 산다.

`emit` 은 Qt 매크로라 식별자로 쓸 수 없다. 람다 이름이 `emitBar` 였던 이유이고,
지금은 단면별 색을 쓰면서 그 람다 자체가 사라졌다.

### 13-63. 같은 것은 같은 함수로 — 화면 축척 탐침을 걷어내다 (2026-08-13)

13-62 에서 목표선의 입체감을 위해 화면 축척을 따로 재는 코드(`addScreenRibbon`)를
넣었다. 두 점을 투영해 화면 픽셀 거리를 재고 그것으로 두께를 정하는 함수였다.
결론부터: **불필요했다.**

목표선도 코리도 테두리도 지면 위의 선이다. 월드에서 폭을 주면 투영이 같은 원근을
알아서 준다. 화면에서 다시 재는 것은 이미 투영이 한 일을 손으로 되풀이하는
것이고, 되풀이하는 순간 두 요소가 **다른 경로로 두께를 얻는다** — 지금은 값이
맞더라도 투영식이 바뀌면 갈라진다. 목표선이 코리도와 어긋나 보이면 그것은
"조향이 다르다"로 읽혀야 하는 신호인데, 축척 차이가 같은 그림을 만든다.

그래서 하나로 합쳤다:

```cpp
void WorldItem::addWorldRibbon(VertexBuffer& out, const std::vector<Vec2>& center,
                               float half_m, const std::vector<Rgba>& colors) const {
  if (center.size() < 2) return;
  std::vector<Vec2> a, b;
  offsetPath(center, half_m, a, b);
  addFilledStripShaded(out, a, b, colors);
}
```

테두리는 `addWorldRibbon(out, left, rim_m, rim)` 을 좌우로 두 번, 목표선은
같은 함수를 `half_m = 0.08` 로 부른다. 같은 배율을 **규약이 아니라 구조로**
보장한다.

측정: 목표선 두께 `y250=41 y400=46 y550=50 y700=55`, 원근비 1.31 → **1.34배**.
사실상 그대로다. 즉 축척은 이미 같았고 탐침은 **틀린 게 아니라 군더더기**였다.
없앨 이유로는 그것으로 충분하다.

같은 김에 `addFilledStrip` 도 지웠다 — 단색 버전은 `addFilledStripShaded` 에
같은 색 두 개를 넘기면 되고, 호출부가 하나였다.

| | 전 | 후 |
|---|---|---|
| `src/world_item.cpp` | 1138줄 | **1042줄** |
| `include/hero_hud/world_item.hpp` | 179줄 | **174줄** |
| 리본 그리는 함수 | 3개 | **1개** |

렌더 결과 화소차 평균 1.45, 다른 화소 1.14% (시나리오 타이밍 지터 수준).
테스트 42개 통과.

남은 것: `drawCorridor` 는 여전히 626줄이다. 함수를 합치는 것과 god function 을
쪼개는 것은 반대 방향처럼 보이지만 같은 요구다 — **한 가지 일을 하는 단위**로
만드는 것. 요소별 레이어(테두리·채움·눈금·정지선·목표선)로 나누는 것이 다음
단계이고, 지금 안 한 것은 람다들이 지역 상태(`left`/`right`/`colors`/`block`)를
넓게 잡고 있어 컨텍스트 구조체 없이는 못 빼기 때문이다. 그 구조체를 설계하는
것이 실제 작업이다.

### 13-62. 세 가지 결함 — 정지선·정합·눈금 (2026-08-13)

**하나. 정지선이 가장 급할 때 사라졌다.**

```cpp
if (!block.known || block.index < 1 || block.index >= last) block.known = false;
```

`block.index < 1` — 막힘이 자차 바로 앞(표본 0)이면 버렸다. **정지선이 가장
필요한 순간에 정지선을 지우는** 조건이었다. 실측으로 t=9 s 이후 사라졌다.
조건을 걷어내고, `drawGroundBar` 의 단면 위치도 범위 밖에서 실패하지 않고
끝으로 붙게 했다 — 막힘이 코앞이면 단면 하나가 음수 호길이로 가는데 거기서
포기하면 같은 결과가 된다.

**둘. `approach` 만 계획을 추종하지 않았다.**

| | 어긋남 평균 | 최대 |
|---|---|---|
| approach (이전) | **131.1 px** | 379.5 |
| approach (지금) | 4.2 px | 6.7 |
| arrive | 8.8 px | 243.3 |
| cruise | 2.1 px | 6.8 |

13-51 에서 순수 추종을 `cruise` 와 `arrive` 에만 넣고 `approach` 는 대본 조향
그대로 뒀다. 내가 "드라이브바이"라고 비판해 놓고 고치지 않은 그 시나리오다.
`approachIdeal()` 을 헬퍼로 빼서 제어와 발행이 같은 경로를 쓰게 했다.

**셋. 후진에서 눈금이 줄무늬가 됐다.**

후진은 코리도가 좁고 근거리가 압축되어 눈금 셋이 붙는다. 붙은 눈금은 **저하
상태의 줄무늬와 같은 그림**이고, 13-40 에서 가로 막대를 버린 이유가 바로
그것이었는데 후진에서 되살아나 있었다. 간격 요구를 최소 간격의 2.5배로 올려
한 쌍만 남게 했다.

**측정 지표를 세 번 잘못 잡았다.** 가로선을 셀 때 코리도 테두리와 화살촉까지
세어 "안 고쳐졌다"는 결론을 냈다. 확대해 눈으로 보고서야 한 쌍만 남은 것을
확인했다. **무엇을 세고 있는지 먼저 확인해야 한다.**

### 13-61. 화면이 정신 사나웠다 — 그리고 고치다 관계를 뒤집을 뻔했다 (2026-08-13)

"화면이 획획 바뀐다"는 지적. 0.1초 간격으로 뜯어보니 튀는 것이 **투영이 아니라
표시 상태**였다.

```
6.7 s 적색+정지선 → 6.9 s 회색 → 7.2 s 적색 → 7.4 s 회색
```

**막힘이 붙었다 떨어졌다 했다.** 코리도가 주차차량을 스치며 지나가면 붉음과
정지선이 통째로 나타났다 사라진다. 여기에 임계 점멸(0.55 s)이 겹치면 무엇이
점멸이고 무엇이 상태 변화인지 구별되지 않는다.

**막힘을 0.7 s 붙들어 둔다.** 위험이 방금 있었다면 지금도 있을 가능성이 높다.
프레임간 화소차 90분위가 4.91 → 3.97 로 줄었다 — 평균은 그대로이고 **튀는
순간만** 줄었다.

**투영(지평·좌우 창)도 시간 평활했다.** 원래 이것이 원인이라고 생각했는데
재보니 기여가 거의 없었다(프레임간 폭 변화 19.1 → 19.2 px). 그래도 맞는 변경
이므로 남겼다 — 속도와 조향에서 매 프레임 다시 계산하면 카메라가 계속 줌한다.

**그리고 여기서 크게 잘못했다.** 목표 호의 곡률에도 평활을 넣었다. 그 결과:

| 꺾는 구간 어긋남 | 평활 있음 | 평활 제거 |
|---|---|---|
| t=5 s | +78 px | 0 px |
| t=6 s | −35 px | −11 px |
| t=8 s | −40 px | −21 px |

**목표가 늦어져 코리도가 목표를 앞질렀다.** 이 화면에서 둘의 관계는 정해져
있다 — **목표가 앞서고 코리도가 따라간다.** 사람이 핸들을 돌리는 데 시간이
걸리기 때문이다. 목표를 평활하면 그 관계가 뒤집히고, 화면의 뜻 자체가 거짓이
된다. 사용자가 "코리도가 가이드보다 빨리 움직인다"고 정확히 짚었다.

게다가 계수를 프레임 시간 0.05 s 고정으로 썼는데 렌더는 60 fps 라 실제 시상수가
3배로 늘어 있었다.

**교훈.** 어지러움을 줄이려고 **표시의 의미를 나르는 값**을 평활하면 안 된다.
평활해도 되는 것은 카메라(투영)와 잡음(막힘의 스침)이고, 목표와 현재의 관계는
건드리면 안 된다. 계획이 튀는 것은 상류의 문제이고 `hero_coach` 가 안정된 계획을
내야 한다 — 표시가 그것을 감추면 안 된다.

### 13-60. 목표선에 원근을, 크게 꺾을 때는 지평을 줄인다 (2026-08-13)

**목표선만 원근이 없었다.** 13-39 에서 화면 고정 두께로 바꾼 것은 월드 폭으로
그렸을 때 가까운 쪽이 쐐기처럼 두껍고 먼 쪽이 소실되어 "선이 아니라 삼각형"이
됐기 때문이다. 그런데 그 결정이 **정지선과 정반대**였다 — 정지선은 지면 위의
것이라 거리에 따라 가늘어지는데, 목표선도 지면 위의 선이다. 고정 두께면 화면에
붙은 것처럼 보인다.

정지선이 쓰는 방식이 답이었다. **월드 두께(0.16 m)로 원근을 따르되 획 두께를
하한으로 삼는다.** 그러면 가까운 쪽은 원근대로 굵고 먼 쪽은 읽히는 최소 굵기로
남아, 삼각형 문제도 안 생긴다. 실측 42 px(먼 쪽) → 56 px(가까운 쪽), 하한
34.6 px 위.

자리마다의 화면 축척은 **월드에서 옆으로 0.2 m 옮긴 점을 투영해** 픽셀 거리로
잰다. 투영이 비선형이므로 식으로 유도하지 않고 직접 잰다.

**크게 꺾을 때 지평을 줄인다.** 곡률이 크면 호가 감겨 중간이 부풀고 화면
가장자리로 밀려난다. 속도만으로 지평을 정한 것이 반쪽이었다 — 곡률도 봐야 한다.
호가 `max_turn_rad`(0.9 rad) 이상 감기지 않도록 지평을 자른다. 물리적으로도
맞는다: 크게 꺾는 것은 저속 기동이고 그때 40 m 앞을 볼 이유가 없다.

효과(코리도 폭, y=520):

| 시각 | 이전 | 지금 |
|---|---|---|
| 7.0 s | 167 px | 163 px |
| 7.5 s | 130 px | 229 px |
| 8.0 s | **0 px** | 160 px |

**여전히 남는 것.** 7~8 s 에서 코리도가 화면 왼쪽에 붙은 얇은 곡선으로 남는다.
좁은 화각에서 크게 감기는 호를 **전부 보여주면서 굵게 유지하는 것은 불가능하다** —
담는 조정과 읽히게 하는 조정이 반대로 당긴다(13-59). 지금은 "잘리되 남는다"
쪽에 서 있다.

### 13-59. 빈 화면 경고(X)가 떴다 — 내가 만든 것이었다 (2026-08-12)

`arrive` 7.2~7.4 s 에서 화면에 앰버 X 두 줄만 남았다. 빈 화면 경고다 — "그릴
것은 있는데 화면에 하나도 안 담겼다". 검게 두면 "앞이 깨끗하다"로 읽히므로
표시가 실패했음을 명시하는 장치인데, 그것이 실제로 발동했다.

**원인 둘 다 13-56 에서 내가 넣은 것이다.**

**하나. 최대 변위가 아니라 끝점 변위를 썼다.** `(1 − cos(k s)) / k` 는 호 **끝**의
변위다. 호가 90도를 넘게 감기면 끝점은 되돌아오지만 중간이 부푼다. 최대 변위가
9.9 m 인 장면에서 이 식은 0.36 m 를 냈고 창이 최소폭으로 잡혔다. 반원을 넘기면
최대 변위는 지름(2/k)이다.

**둘. 창 확장이 가독성 검사와 싸웠다.** 이게 더 근본적이다.

```
창 ±11.4 m  →  코리도 폭 102 px
legibleRange 하한 = 분해 간격 x 3 = 103.8 px
→ 첫 표본부터 실격 → drawCorridor 가 즉시 반환 → 아무것도 안 그림
```

**화면 안에 넣으려다 읽을 수 없게 만들었다.** 창을 넓히면 코리도가 좁아지고,
어느 지점부터는 좁아진 것이 잘린 것보다 나쁘다 — 잘리면 앞부분이라도 제대로
보이지만, 좁아지면 통째로 사라진다.

**가독성이 창 넓이의 상한을 정한다.** 코리도가 하한 굵기를 유지하는 폭까지만
넓히고, 그 뒤로는 넓히는 대신 자른다.

```
lateral_half ≤ 차폭 x 화면폭 / (2 x 분해간격 x 3.2)  ≈ 10.5 m
```

**교훈.** 화면에 담으려는 조정과 읽히게 하려는 조정은 **서로 반대 방향으로 당긴다.**
둘 중 하나만 보고 값을 정하면 다른 쪽이 조용히 무너진다. 13-56 은 담는 것만 봤다.

### 13-58. 붉음의 깜빡임 — 장애물이 경로 밖에 있었다 (2026-08-11)

막힘이 붙었다 떨어졌다 하며 붉음이 깜빡였다. 원인은 **장애물이 경로 밖에 있고
코리도가 그것을 스치며 지나간 것**이다. `approach` 를 두고 지적했던 결함이
`arrive` 에도 그대로 있었다.

전진 중 코리도가 슬롯 쪽으로 꺾이며 옆 주차차량을 스쳤고, 조향이 되돌아오면
다시 떨어졌다. 슬롯 앞차를 정지 지점 너머로 빼니 큰 붉음이 짧은 스침으로 줄었다.

```
이전: .......#........###.....     (# 큼, + 작음, . 없음)
지금: ......+.......####......
```

후진 구간이 연속(`####`)이 된 것이 핵심이다 — **연석까지의 거리가 단조롭게
줄어들고, 그것이 감속 그라데이션과 정지선이 설계대로 도는 유일한 조건이다.**

**한 번 크게 헛짚었다.** "전진 중에는 차선을 유지하고 지나친 뒤 후진한다"로
계획을 바꿨더니 붉음이 통째로 사라졌다 — 그리고 차선에서 슬롯으로 바로 후진하는
계획이 되어 목표 호가 **거의 원**이 됐다. 읽을 수 없는 화면이다. 되돌렸다.

실제 순서가 그렇다는 것과 **하나의 호로 표현할 수 있다는 것은 다르다.** 두 구간
(지나치기 · 넣기)을 잇는 계획은 `hero_coach` 가 낼 일이고, 목 발행 노드의 단일
에르미트로는 안 된다. 13-52 에 적은 것과 같은 한계다.

### 13-57. 주차 완료는 이미 있는 요소들이 말한다 (2026-08-11)

"댔다"를 말하는 요소가 없었다. 후진이 끝나도 화면은 여전히 "저 앞이 막혔다"를
그리고 있었고, 끝났다는 신호가 없었다.

**새 심볼을 더하지 않는다.** 완료는 이미 있는 셋의 조합이다:

> **정지선이 가장 가까운 눈금에 닿고, 기어가 P 로 간다.**

눈금이 자이고, 정지선이 지금 값이고, P 가 상태다. 각각은 이미 제 일을 하고
있었고 완료는 그 셋이 동시에 참인 순간일 뿐이다. 이 화면의 어법("새 심볼이
아니라 같은 도형의 색과 마감")과도 맞는다.

**두 곳을 고쳐야 그 그림이 나왔다.**

- 시나리오에 **슬롯 안쪽 끝(연석)** 이 없었다. 후진이 끝나는 자리 뒤에 두어야
  정지선이 눈금까지 내려온다. 없을 때는 옆 주차차량이 잡혀 "앞이 막혔다"로
  읽혔다
- **정지선에 닿는 눈금이 내 규칙에 지워지고 있었다.** 13-55 에서 "정지선 너머는
  긋지 않는다"를 `d >= s_block` 으로 썼는데, 완료의 순간은 정확히 `d == s_block`
  이다. 완료를 그리려는 규칙이 완료를 지우고 있었다. `d > s_block + 0.06` 으로
  고쳤다

읽히는 순서: 붉음이 좁혀 들어온다 → 정지선이 눈금까지 내려온다 → 앰버 P →
녹색 + P. `docs/screens/hud_arrive_done.png`.

### 13-56. 좌우 창을 코리도의 실제 휨에서 유도한다 (2026-08-11)

목표가 차선에서 슬롯으로 꺾이는 구간(t≈5~7 s)에서 **코리도가 화면 밖으로 쓸려
나갔다.** 화면에 가느다란 조각만 남았고, 그것은 "슬롯이 저쪽이다"가 아니라
"뭔가 잘못됐다"로 읽힌다. 흐림에서는 더 그렇다.

원인은 좌우 창을 **깊이의 고정 비율(6%)** 로 잡은 것이다. 코리도가 실제로 얼마나
휘는지와 아무 관계가 없는 값이었다. 13-49 에서 지평만 시간으로 바꾸고 좌우는
비율로 둔 것이 반쪽이었다.

일정 곡률 호의 횡변위는 `(1 − cos(κ s)) / κ` 다. 조향과 지평에서 그것을 계산해
담을 만큼 창을 넓힌다. **조향이 커지면 창도 같이 넓어지므로 코리도가 원리적으로
화면을 벗어날 수 없다.**

대가는 크게 꺾는 동안 코리도가 화면에서 얇아지는 것이다. 그래도 **잘려 나가는
것보다 얇아지는 편이 낫다** — 잘리면 무엇이 일어나는지 알 수 없고, 얇아지면
"많이 꺾는 중"이 그대로 읽힌다.

### 13-55. 눈금이 정지선을 넘고 있었다 (2026-08-11)

거리 눈금이 **갈 수 없는 자리를 재고 있었다.** `arrive` t=10 s 에서 정지선이
0.35 m 인데 0.6 · 1.0 m 눈금이 그 너머에 떠 있었다. 눈금은 "여기까지 얼마"를
재는 자인데, 도달할 수 없는 거리를 재면 그것은 거짓이다.

정지선 너머는 긋지 않는다. 상류가 막힘을 모르면(정지선이 없으면) 전부 긋는다 —
모르는 것을 이유로 지우지는 않는다.

**두께를 균일하게 했다.** 정지선은 지면 위의 것이라 거리에 따라 줄어야 하지만
(13-40), 거리 눈금은 **자를 읽는 눈금**이지 지면에 놓인 물체가 아니다. 눈금마다
굵기가 다르면 "무엇이 굵은 눈금인가"를 묻게 되는데 실제로는 아무 뜻도 없다.
`drawGroundBar` 에 균일 모드를 더해 화면 두께를 획 두께로 맞춘다 — 넓히기만
하던 하한 보정과 달리 좁히기도 한다.

이 둘은 서로 반대 방향의 결정이고, 그것이 맞다. **정지선은 지면의 사건이고
눈금은 화면의 자다.**

### 13-54. 추종이 안 되던 진짜 이유 — 전방주시거리가 서로 달랐다 (2026-08-11)

목 차량이 계획을 따라가는데도 코리도와 목표 호가 겹치지 않았다. 눈으로는
"추종이 엉망"으로 보였다. 원인은 제어가 아니라 **두 곳이 서로 다른 거리를
보고 있었던 것**이다.

| 속도 | HUD 가 호를 뽑는 거리 | 목 차량이 추종하는 거리 |
|---|---|---|
| 5 m/s | 3.8 m | 6.0 m |
| 11 m/s | **8.2 m** | **13.2 m** |
| 13.9 m/s | 10.4 m | 16.0 m |

전방주시거리가 다르면 곡률이 다르다. **완벽히 추종해도 두 선은 영영 겹치지
않는다.** 같은 규칙(`range = clamp(|v|×3, 6, 60)`, `look = max(3.5, range×0.25)`)을
양쪽이 쓰게 했다.

실측(코리도 중심 대비 목표 호 중심, px):

| 구간 | 거리 불일치 | 일치 | 하한 3.5 m |
|---|---|---|---|
| 전진 | 2.6 | 1.4 | 7.5 |
| 후진 | — | 101.1 | **1.4** |

**후진이 특히 나빴던 것은 전방주시 하한이 2 m 였기 때문이다.** 후진 범위가
최소 6 m 라 look 이 2 m 로 걸렸고, 2 m 앞 점의 곡률은 잡음에 예민해 조향이
계속 흔들렸다. 하한을 3.5 m 로 올리니 101 → 1.4 px 가 됐다. 전진은 저속 구간에서
하한이 걸려 1.9 → 7.5 px 로 조금 나빠졌지만 여전히 작다.

**같은 값을 두 곳에서 따로 정하면 언젠가 어긋난다.** 지금은 규칙을 복제해
두었고(목 발행 노드는 HUD 설정을 모른다), `hero_coach` 가 생기면 곡률을 상류가
직접 주는 편이 낫다 — 그러면 이 종류의 불일치가 원천적으로 없어진다.

### 13-53. 조향을 목표로 **점진 수렴**시킨다 (2026-08-11)

13-52 에서 후진 추종을 포기했는데, 두 가지가 틀렸다.

**첫째, 부호를 뒤집은 것이 원인이었다.** 자전거 모델에서 경로 곡률은
`tan(δ)/L` 이고 **진행 방향과 무관하다** — 같은 조향이 같은 원을 그리고, 후진은
그 원을 반대로 돌 뿐이다. 그러므로 후방 목표점에도 같은 부호의 조향을 써야 한다.
`-pursue(...)` 로 뒤집었더니 목표에서 멀어지는 쪽으로 감기며 조향이 튀었다.

**둘째, 제어기를 세울 필요가 없었다.** 가상 시연이므로 대본이 내는 조향을
**목표**로 보고, 실제 조향이 고정 속도(0.55 rad/s)로 거기 수렴하게 하면 된다.
한 걸음에 한 스텝만 움직이므로 어떤 목표가 와도 튀지 않는다.

이 한 줄이 화면에도 옳다. 목표를 그대로 실제 조향으로 쓰면 계획이 꺾이는 순간
핸들이 순간이동하는데, **이 화면이 보여주려는 것이 코리도가 목표 호로 다가가는
과정**이다. 순간이동하면 그 과정 자체가 없다.

**후진에 코리도와 목표 호가 함께 나온다.** 조향이 튀지 않으니 코리도가 얇아지지
않고, 계획을 계속 내므로 호도 남는다.

여전히 t≈10~11 s 에서 호가 잠깐 사라진다 — 계획이 전진에서 후진으로 넘어가며
곡률이 부호를 바꾸는 지점이다. 목 시나리오가 두 구간을 따로 만들기 때문이고,
`hero_coach` 는 하나의 연속 계획을 내야 한다.

### 13-52. 목표선을 계획 전체에서 **호**로 (2026-08-11)

목표선이 계획을 통째로 그리고 있었다. 굽이치는 자유 곡선은 "어긋난 오버레이"로
읽히고(13-33 의 콜드 리드가 실제로 그렇게 답했다), 시력 0.1 에서 곡선의 형태를
읽는 것은 비싸다.

**계획의 자차 부근 곡률 하나를 뽑아 같은 길이의 호로 그린다.** 그러면 코리도와
목표선이 **같은 종류의 물체**가 된다 — 둘 다 "이 조향을 유지하면 지나갈 자리"다.
벌어진 각도가 곧 **핸들을 얼마나 돌려야 하는가**이고, 그것이 사용자가 지금 해야
할 단 하나의 행동이다.

대가는 계획의 먼 쪽 형태를 버리는 것이다. 어디로 가는지는 알 수 없고 지금 무엇을
할지만 남는다 — 주차든 차선 유지든 사용자가 실제로 쓰는 것은 후자다.

**후진에 목표선이 아예 없었다.** 시나리오가 슬롯이 뒤로 넘어가면 빈 리본을 보내고
있었고, 정작 조향이 가장 어려운 구간에서 기댈 것이 사라졌다. 원인이 둘이었다 —
목 시나리오가 후진 계획을 안 냈고, 슬롯을 자차가 **지나치지 않는 자리**에 두어
후진 중에도 목표가 앞에 있었다. 실제 후진 주차 순서(지나쳐 서고 뒤로 넣는다)로
슬롯을 옮기고, 슬롯이 옆·뒤로 오면 접선을 뒤로 잡은 후진 계획을 내도록 했다.

**후진 추종은 넣지 못했다.** 후방 순수 추종은 목표점이 뒤에 있어 곡률 부호와
전방주시 선택이 함께 뒤집히는데, 부호만 뒤집어 넣었더니 조향이 크게 튀어
코리도가 얇아졌다. 후진 전용 제어기가 필요하고 그것은 목 발행 노드가 감당할
범위를 넘는다. 대본 조향으로 되돌리고 계획만 계속 낸다.

**남은 거친 곳.** 계획이 전진에서 후진으로 넘어가는 순간(t≈9~10 s) 호가 잠깐
사라진다. 곡률이 그 지점에서 부호를 바꾸며 퇴화한다. 전환 자체는 목 시나리오의
한계이고, `hero_coach` 는 두 구간을 잇는 계획을 한 번에 내야 한다.

### 13-51. 목 차량이 계획을 추종하게 했다 (2026-08-11)

목 차량이 **대본대로만 달리고 계획을 무시하고 있었다.** `arrive` 에서 목표가
차선에서 슬롯으로 꺾이는데 차는 그대로 직진했고, 그래서 코리도와 목표선이 늘
크게 벌어진 채였다. 이 화면이 보여주려는 것이 바로 그 둘의 관계인데, 추종하지
않는 차를 띄우면 **매 프레임이 "완전히 어긋난 상태"** 가 된다.

순수 추종(pure pursuit)을 넣었다. 전방주시거리를 속도에 비례해 잡고(3~16 m),
목표점의 곡률에서 조향각을 낸다. 외란을 작게 얹어 완벽히 붙지는 않게 한다 —
코리도와 목표선이 늘 정확히 겹치면 그 둘을 비교하는 화면의 의미가 없다.

**제어와 발행이 같은 경로를 써야 한다.** `arriveIdeal()` 을 헬퍼로 빼서 차가
따라가는 길과 화면에 그리는 길이 갈라지지 않게 했다. 따로 만들면 화면이
거짓말을 한다.

이전에 쓰던 횡오차·헤딩오차 되먹임은 걷어냈다. 그것은 **차선 유지**는 하지만
**계획 추종**은 아니다 — 슬롯으로 꺾이는 목표를 따라갈 수 없다.

`approach` 는 아직 추종하지 않는다. 목표를 8 m 지나쳐 15 m 까지 갔다가 돌아오는
드라이브바이 그대로다(내 비판 2번). `arrive` 가 추종하는 주차 기동을 담으므로
`approach` 가 필요한지부터 다시 볼 일이다.

### 13-50. 전환을 보는 대본 (2026-08-11)

`approach` 는 계속 주차이고 `cruise` 는 계속 주행이라, **13-48 의 판별기가 실제로
넘어가는 장면이 어느 대본에도 없었다.** 단위 시험으로만 확인한 상태였다.

`arrive` 를 더했다. 주행 → 슬롯 발견 → 감속 → 정지 → 후진 주차 → 복귀.

| 시각 | 화면 |
|---|---|
| 0~5 s | 주행. 눈금 없음, 시간 지평, 차선 리드 |
| 6 s | 주차 표지가 뜬다 (슬롯이 잡혔다) |
| 7~9 s | 목표가 차선에서 슬롯으로 넘어간다. 아직 주행 어법 |
| 10~11 s | **거리 눈금이 뜬다** — 어법이 주차로 넘어갔다 |
| 12~13 s | 앰버 R (권고), 정지하면 녹색 |
| 14~21 s | 후진. 화살촉 + 눈금 |
| 22~24 s | P, 그리고 주행으로 복귀 |

목표가 차선에서 슬롯으로 넘어가는 것은 **상류가 실제로 하는 일**이다 — 멀리서는
차선을 따라 리드하고, 슬롯이 잡히면 그리로 가는 계획을 낸다. 끝점이 12 m 안으로
들어오고 저속이 되면 HUD 가 그것을 읽는다.

후진이 주행 대본에 없는 것은 결함이 아니다. 후진은 주차 어법이고 50 km/h 대본에
들어갈 자리가 없다. 다만 **전환을 보는 대본이 없었던 것은 결함이었다.**

### 13-49. 시간 지평과 주행 시나리오 (2026-08-11)

13-47 이 적은 문제를 실제로 고쳤다. 담는 깊이를 고정 미터에서 **시간**으로 바꾼다.

```
range = clamp(|속도| x 3.0 s, 6 m, 60 m)
```

저속에서는 min 6 m 가 걸리므로 **주차 그림은 그대로다** — 13절까지의 시각 판단이
살아남는다. 50 km/h 에서는 41.7 m 가 된다.

**한 군데만 바꿔서는 안 됐다.** 세 가지가 같이 따라가야 한다.

- **현재궤적 길이.** `path_length_m` 8 m 고정을 그대로 두었더니 코리도가 화면
  아래 3분의 1에서 뚝 끊기고 위는 검게 남았다. 투영은 41.7 m 를 담는데 기하는
  8 m 였다
- **좌우 폭.** `lateral_half_m` ±1.8 m 도 주차용이다. 40 m 앞을 보면 조향
  0.012 rad 만으로도 횡변위가 3.6 m 라 코리도가 화면 밖으로 나간다. 깊이에
  비례(0.06)해 늘린다
- **위협 등급.** 거리(3 m)가 아니라 **남은 시간**으로 잡는다. 50 km/h 에서
  15 m 는 1.1 초다

**주행 시나리오(`cruise`).** 50 km/h, 차선 유지, 선행차 접근, 황→적 신호, 속도
제한 표지.

목표 경로는 **차선에서 만든다.** 차선 중심선(월드 y=0)을 base_link 로 옮기고
smoothstep 으로 자차에 붙인다 — b(0)=0, b'(0)=0 이라 계약("자차에서 시작하고
첫 접선이 진행 방향")을 지킨다. 차선을 그대로 보내면 원점이 달라 코리도와의
비교가 성립하지 않는다. 그리고 지평까지 뻗어야 주차 계획으로 오인되지 않는다.

**개루프 조향으로는 차선 유지가 안 됐다.** 사인으로 흔들었더니 진폭을 0.0022 rad
까지 줄여도 반주기 79 m 동안 한쪽으로 2.5 m 적분되어 차선을 통째로 나갔다.
실제 운전처럼 **되돌리는 피드백**(횡오차·헤딩오차 되먹임 + 작은 외란)을 넣으니
비로소 "조금 벌어졌다 되돌아온다"가 나온다.

**주차 대본의 결함 하나가 여기서 고쳐졌다.** 주차 장애물은 전부 코리도 밖에
있어 조향에 따라 스쳤다 말았다 했는데(내 비판 3번), 주행에서는 선행차를 차선
안에 두어 거리가 단조롭게 줄어든다. 감속 그라데이션과 정지선이 설계대로 동작하는
것을 처음으로 확인했다.

**내가 낸 버그를 하나 잡았다.** 13-45 의 녹↔적 보간에서 조건을 `base_hue.g ==
kGreen.g` 로 썼는데 **kWhite.g 도 255** 라 백색에서도 참이 됐다. 정지가 아닌
감속 그라데이션 한가운데에 녹색이 섞였고(측정 (63,118,70)), 그대로 커밋된
캡처와 영상에 들어갔다. 색으로 상태를 넘겨짚은 것이 원인이다 — `stopped` 를
그대로 쓴다. **주차 화면만 보고 넘어가서 놓쳤다. 주행 시나리오를 만들다 나왔다.**

`HERO_HUD_SCREEN` / `HERO_HUD_FULLSCREEN` 을 더했다. 확장 모니터 시연용이고
Orin 의 전체화면 기동에도 쓴다. 해상도가 달라져도 설계는 따라온다 — 화각은
패널의 물리 치수와 광로에서 나오고 각도 예산이 거기서 픽셀을 유도하므로,
1280x800 설정을 1920x1080 에 띄워도 비율이 유지된다. 다만 **켜진 면적이
22~25% 로 올라간다**(기록된 상한 12~18%). 16:10 을 16:9 에 채운 탓이고, 실제
패널 종횡비가 정해지면 다시 재야 한다.

### 13-48. 주차인지 주행인지는 궤적이 말해준다 (2026-08-11)

표시 어법을 무엇으로 가를지가 문제였다. 기어로 가르면 `D` 로 하는 전진 주차를
놓치고, 속도로만 가르면 신호 대기와 정체가 주차로 읽힌다.

**목표 경로의 끝점이 구분자다.** 주행에서 경로는 시간 지평까지 뻗고, 주차에서는
슬롯에서 끝난다. 저속은 그것을 확인해 주는 두 번째 조건이다.

```
끝점 < 12 m  AND  |속도| < 2.8 m/s  →  주차
```

**여기에 딸린 계약이 하나 생긴다.** 주행의 목표 경로는 **지평까지 뻗어야 한다.**
차선 인식 거리가 짧다고 경로를 짧게 끊어 보내면 그것이 주차 계획으로 오인된다.
`hero_coach` 가 지킬 규칙이다.

**세 가지를 같이 넣었다.**

- **이력(dwell 0.6 s).** 임계 근처에서 표시 어법이 앞뒤로 뒤집히는 것은 어느
  한쪽으로 붙어 있는 것보다 나쁘다. 조건이 유지될 때만 넘어간다
- **CAN 으로의 후퇴.** 경로는 인지 계층이라 죽을 수 있다. 없으면 후진은 주차로
  보고, 그 외에는 직전 판단을 유지한다. 판단 근거가 사라졌다고 어법이 바뀌면
  안 된다
- **주차 전용 요소를 여기 걸었다.** 거리 눈금(50 km/h 에서 0.07초)과 정지 녹색
  (신호 대기마다 화면이 녹색이 되면 정보가 아니라 배경이다). 후진 화살촉은
  이미 기어로 잠겨 있다

**이것은 상류가 아는 것을 아래에서 추론하는 것이다.** `hero_coach` 가 생기면
"주차 기동 중"을 명시로 주는 편이 낫고, 그때 이 추론은 그 신호가 없을 때의
대비책으로 남는다. 지금 추론으로 가는 이유는 계약을 안 바꾸고 오늘 동작하기
때문이다.

`src/hud_state.cpp` 를 `hero_hud_core` 로 옮겼다 — Qt·ROS 의존이 없는데 렌더러
안에만 있어서 테스트를 걸 수 없었다. 판단 로직 시험 5개를 추가했다(전환 지연,
저속+먼 목표는 주행, 경로 없을 때 후퇴, 짧은 이탈에 안 뒤집힘).

**목 시나리오로는 주행 쪽을 검증할 수 없다.** 지금 목은 `has_ideal` 이 대부분
false 라(13-47 의 게이팅) 주차로 래치된 채 머문다. 주행 시나리오가 필요하다.

### 13-47. 범위를 잘못 잡고 있었다 — 주행 보조도 맡는다 (2026-08-11)

13절까지의 모든 숫자는 **주차 기동(1.5 m/s 언저리)** 을 전제로 골랐다. 주행
보조도 맡는다면 그 전제가 깨진다. 현재 값이 속도별로 몇 초가 되는지:

| 속도 | 코리도 범위 6 m | 경로 8 m | 급함 판정 3 m | 거리 눈금 1.0 m |
|---|---|---|---|---|
| 5 km/h | 4.32 s | 5.76 s | 2.16 s | 0.72 s |
| 30 km/h | 0.72 s | 0.96 s | 0.36 s | 0.12 s |
| 50 km/h | **0.43 s** | 0.58 s | **0.22 s** | 0.07 s |
| 80 km/h | 0.27 s | 0.36 s | 0.14 s | 0.04 s |

차간거리 권장이 2 s 이고 50 km/h 정지거리가 25~30 m 다. **50 km/h 에서 이 화면은
0.43 초 앞까지만 보여주고, 충돌 0.22 초 전에야 붉어지기 시작한다.** 주행에서는
표시가 아니라 사후 보고다.

**근본 원인은 모든 공간 값이 고정 미터라는 것이다.** 주차에서는 미터가 맞는
단위였다 — 연석까지 30 cm 인지 60 cm 인지가 그대로 의미다. 주행에서는 시간이
단위다. 같은 30 m 가 5 km/h 에서는 한참 뒤이고 80 km/h 에서는 1.3 초다.

**한 군데만 바꾸면 대부분이 따라온다.** 코리도 범위를 고정 6 m 가 아니라 **주행
시간 지평**(예: 3 s)으로 잡으면:

| 속도 | 3 s 지평 |
|---|---|
| 5 km/h | 4.2 m |
| 30 km/h | 25.0 m |
| 50 km/h | 41.7 m |
| 80 km/h | 66.7 m |

주차 속도에서는 지금과 거의 같은 그림이 나오므로 **13절까지의 시각 판단이
살아남는다.** 속도가 붙으면 범위가 늘어난다. 급함 판정과 감속 그라데이션도 같은
방식으로 거리가 아니라 **충돌까지 남은 시간**으로 잡아야 한다.

바뀌지 않는 것도 있다. 각도 예산(획·심볼·간격)은 시력에서 나오므로 속도와
무관하다. 두 계층 신뢰도, 저하 상태 넷, 팔레트, 점멸 규칙도 그대로다.

**이 정정으로 내가 앞서 한 비판 하나가 무효가 된다.** "주차장에 신호등이 있을
일이 거의 없다"고 적었는데, 주행 보조를 맡으면 신호등과 표지판은 비현실적
픽스처가 아니라 **핵심 입력**이다. 13-46 의 녹색 억제 결론은 유지되지만 근거가
하나 줄어든다 — 실측(주의를 뺏고 뜻이 틀리게 읽힌다)은 그대로이고, "주차 중
진행 허가는 행동 정보가 아니다"라는 의미 논증은 주행에서는 약해진다. 정지 후
녹색으로 바뀌는 **전환**은 주행에서 행동을 요구한다.

### 13-46. 녹색 억제를 다시 시험했다 — 규칙은 유지된다 (2026-08-11)

13-33 에서 녹색을 지운 근거는 콜드 리드였다. 그런데 그 뒤 2차에서 **근본 원인이
따로 드러났고**(코리도가 경계 없는 확산이라 약했다) 테두리로 고쳤다. 즉 녹색
억제는 증상 치료였고, 원인이 해결된 뒤로 녹색을 다시 시험한 적이 없었다.
게다가 13-45 로 신호가 예산대로 커졌으니 조건이 또 달라졌다. 다시 쟀다.

**시험 설계.** 같은 프레임에 녹색 원(예산 크기 224 px)만 합성해 얹은 판과 얹지
않은 판. 두 이미지는 그 원 자리(39,600 화소) 외에는 **완전히 동일**하다 — 두 번
따로 찍으면 시나리오가 그 사이 진행해 화면 전체가 달라져 비교가 안 된다.
맥락 없이 각각 독립으로 물었다.

**결과.**

| | 가장 먼저 눈에 들어오는 것 | 가장 중요해 보이는 것 |
|---|---|---|
| 녹색 없음 | 코리도 + 목표선 | 코리도 + 목표선 |
| 녹색 있음 | **큰 초록색 원** | 초록 원 + 코리도 |

**테두리를 준 뒤에도 녹색은 여전히 1위를 뺏는다.** 코리도가 제 자리를 찾은 것은
확인됐다(녹색 없는 판에서 1위). 그런데 녹색을 넣으면 그 위로 올라간다.

그리고 **의미까지 틀리게 읽힌다.** 초록 원을 신호로 읽지 않았다:

> 초록색 원은 **목표 지점이나 감지된 대상**처럼 보입니다.

즉 대가가 주의 배분만이 아니다. 상단 중앙의 큰 초록 원은 "가도 좋다"가 아니라
**"저기가 목표다" 또는 "무언가를 감지했다"** 로 읽힌다. 가장 안 중요한 정보에
가장 센 자리를 주고, 그 자리에서 다른 뜻으로 읽히는 셈이다. 규칙을 유지한다.

**덤으로 나온 것 둘.**

- **P 표지판이 "버튼"으로 읽혔다** — "주차 관련 상태/버튼". 도로 표지가 아니라
  누르는 것으로 읽혔다. 표지판 표시 규칙(14절)에 이 관찰을 붙인다.
- **거리 눈금은 두 판 모두에서 언급되지 않았다.** 13-42 의 측정과 일치한다 —
  정안 시야에서도 존재감이 없다. 남길지의 판단 재료가 하나 늘었다.

### 13-45. 신호 크기와 녹↔적 보간 (2026-08-11)

**신호 인디케이터가 각도 예산의 3분의 1이었다.** 크기를 상단 띠 높이
(`zone_top` 0.13)에서 유도하고 있었고, 그 결과 팔각형이 **70 px** 였다. 심볼
최소는 `symbol_detail_multiple` 12 × 분해 한계 = **207.4 px (2°)** 다. 흐림에서
점 하나로 뭉개진 것이 우연이 아니라 계산대로였고, 하마터면 "신호는 시력 0.1
에서 안 보인다"고 적을 뻔했다 — 눈금 때와 같은 오진을 반복할 뻔했다.

예산에서 직접 유도하도록 바꿨다(팔각형 폭 = 2r·cos(π/8) 가 심볼 최소가 되게).
자리는 상단 띠를 조금 넘어 코리도 위에 얹히는데, 신호가 뜨는 순간 그것이 화면에서
가장 급한 정보이므로 그대로 둔다.

다만 **흐림 개선은 제한적이다** — 적색 편차가 30.5 → 37.0 (+21%). 크기를 세 배로
키웠는데 이만큼인 것은, 밝은 배경에서 대비의 분모가 배경 휘도라 크기로는 넘을 수
없는 벽이기 때문이다(13-42와 같은 원인). 어두운 배경에서는 이득이 훨씬 크다.

**주의: 이 절을 쓰기 전 나는 심볼 최소를 103.7 px 로 알고 있었다.** 헤더 기본값
(6.0)만 보고 `config/hud.yaml` 이 12.0 으로 덮는 것을 놓쳤다. **예산 값은 헤더가
아니라 실행 중인 설정에서 읽어야 한다.**

**녹↔적 보간이 카키를 지나고 있었다.** 정지 녹색과 적색을 바로 섞으면 중간이
(99,104,38) — 팔레트에 없는 다섯째 색이고, 하필 앰버(가이드·권고 기어)와 계통이
겹쳐 "이게 가이드인가" 하는 순간을 만든다. 팔레트를 넷으로 좁혀놓고 보간이
그것을 어기고 있었다.

백색을 경유하도록 바꿨다. 녹(멈춰 있다) → 백(중립) → 적(막혔다) 는 셋 다 이미
쓰는 색이고 의미의 순서와도 맞는다. 실측으로 중간이 (163,158,156) 로, 카키가
사라졌다.

### 13-44. 눈금이 2.5D 를 안 따르고 있었다 (2026-08-11)

"두께가 거리를 따른다"고 13-39 에 적어놓고 실제로는 **정반대로 동작하고 있었다.**
계측을 붙여 찍어보니:

```
BAR d=0.30  w=0.162 m  span=34.6 px  floor=34.6
BAR d=0.60  w=0.194 m  span=34.6 px  floor=34.6
BAR d=1.00  w=0.229 m  span=34.6 px  floor=34.6
```

세 눈금 모두 **정확히 하한**이다. 월드 두께(w)가 거리마다 달라지며 화면 두께를
34.6 px 에 맞추고 있었다 — 즉 **화면 고정 두께**이고, 월드 두께가 그 뒤를 따라간
셈이다. 원인은 기준 두께를 0.12 m 로 잡은 것이다. 이 투영에서 0.12 m 는 0.3~1.0 m
전 구간에서 하한보다 얇아, 넓히는 보정이 **항상** 걸렸다.

0.23 m 로 올렸다. 1.0 m 에서 하한과 같아지고 그보다 가까우면 커진다:

```
BAR d=0.30  w=0.230 m  span=49.0 px      (후진 50.3)
BAR d=0.60  w=0.230 m  span=40.8 px      (후진 41.8)
BAR d=1.00  w=0.230 m  span=34.6 px      (후진 35.4)
```

**화면 열로 재서는 못 잡았을 문제다.** 눈금이 조향에 따라 기울어 세로 열이
비스듬히 자르므로 겉보기 두께가 왜곡되고, 실제로 34/25/35 처럼 단조롭지 않은
값이 나와 원인을 오해했다. 기하 값은 코드에서 찍어야 한다.

### 13-43. 페이드는 색이 아니라 알파로 — 미리 곱해진 알파 (2026-08-10)

끝을 코리도 색으로 수렴시키는 방법은 **그 아래 실제로 깔린 색과 정확히 같아야만**
이음매가 없다. 눈금 색은 중심 거리 하나로 잡는데 코리도는 표본마다 다르므로,
어긋난 만큼 옅은 자국이 남는다. 알파를 0 으로 보내면 아래에 무엇이 있든 그것이
그대로 드러난다.

**함정.** 씬그래프는 **미리 곱해진 알파**를 쓴다 — `withAlpha` 가 RGB 를 같이
곱하고 있는 것이 그 규약이다. `a` 만 낮추면 RGB 가 그대로 더해져 **끝이 오히려
밝아진다.** 실제로 눈금 끝이 새하얗게 타올랐다. 네 성분을 함께 줄여야 한다
(`scaleAlpha`).

같은 실수가 목표선 꼬리(`addScreenRibbon` 의 `fade_tail_frac`)에도 있었다.
넣을 때부터 틀려 있었고 이번에 같이 고쳤다.

### 13-42. 눈금을 녹여 잇고, 그러다 잘못된 진단을 했다 (2026-08-10)

안쪽 끝을 직각으로 끊으니 잘린 자국이 남았다. 밝기 굴곡을 만들어 넣는 것은 이미
실패한 길이므로(13-41), **배율만 난간 쪽 전부에서 안쪽 1.0 으로 떨어뜨렸다.**
끝에서 색이 정확히 코리도 색이 되므로 이음매가 사라진다 — 없는 그라데이션을
만드는 것이 아니라 강조가 사그라드는 것이고, 도달하는 색은 코리도 자신의 색이다.
색이 가로로 변해야 하므로 띠를 가로 방향으로 짠다.

**그리고 여기서 내가 한 번 틀린 진단을 했다.** 흐림 뒤에 눈금 대비가 2~3 으로
떨어지는 것을 보고 "거리 눈금은 시력 0.1 에서 보이지 않는다"고 적었다. **틀렸다.**
원인을 분리해 다시 재니 흐림이 아니라 **배경 휘도**였다.

같은 화면, 차단 3.0 cyc/deg, 대비 계수 없이 배경만 바꿔 잰 값:

| 배경 | 눈금 ΔL | 주변 휘도 | Weber 대비 |
|---|---|---|---|
| 검정 | 32.1 | 173 | **18.5%** |
| 야간 | 31.5 | 187 | **16.8%** |
| 흐린 날 | 5.5 | 249 | 2.2% |
| 맑은 낮 | 0.0 | 255 | 0.0% |

**흐림만으로는 눈금이 죽지 않는다.** 어두운 배경에서는 18.5% 로 저시력 문턱
(10~20%)의 위쪽에 있다. 무너지는 것은 배경이 밝아질 때이고, 이유는 4절과 9절이
이미 적어놓은 그대로다 — 가산광에서 Weber 대비의 분모는 **배경 + HUD** 이고,
패널이 더할 수 있는 빛의 양은 정해져 있다. 눈금만의 문제가 아니라 **모든 요소가
같은 벽에 부딪힌다.** 지렛대는 패널 최대 휘도와 컴바이너 투과율뿐이다(하드웨어).

내가 잘못 본 경로는 둘이었다. (1) 측정 기본값이 `--bg overcast` 라 이미 밝은
배경이었고, (2) 거기에 `--csf 0.6` 을 얹었다. 대비 계수는 차단주파수와 **별개의
가정**이라 둘을 곱하면 원인이 섞인다 — 3.5(계수 포함) 대 5.5(계수 없음).
**앞으로 "안 보인다"를 말할 때는 배경과 계수를 분리해 적는다.**

두께는 묶인 변수가 아니었다. 하한을 획 두께의 0.6배에서 예산 그대로
(분해 한계 × 2)로 올려도 값이 거의 변하지 않았다. 예산을 깎을 이유가 없었으므로
되돌려 두었지만, 그것이 눈금을 살린 것은 아니다.

## 14. 미해결 · 미측정

이 절은 13절의 작업이 끝난 시점(2026-08-07) 기준으로 다시 썼다. 이전 판은
그 사이에 해결된 항목을 미해결로 적고 있었다.

**하드웨어가 막고 있는 것**

- **광로 길이 미확정** (민경태). 화각이 10~18° 구간으로 좁혀졌고 그 안에서는
  설계가 성립한다. 값이 나오면 `view_distance_m` 하나만 바꾸면 된다
- **패널 최대 휘도 · 컴바이너 투과율 미확정** (민경태). 9절이 보였듯 주간
  가독성의 지렛대는 이 둘뿐이고, 소프트웨어 게인으로는 넘을 수 없다
- 가상상 화각, 이중상, 아이박스 (민경태) — 13-2가 숫자를 하나 줬다
- 세 번째 카메라의 배치와 기하 (고영우)
- **배경 모형이 합성이다.** `acuity_sim.py`의 배경은 그린 것이지 찍은 것이
  아니다. 마운트 기하에 따라 상단이 하늘인지 보닛인지 갈리고, 그에 따라
  고정 자리 배치의 판단이 바뀐다. CARLA 프레임이나 실차 사진으로 교체해야 한다
- **Orin 실측 0회.** eglfs 기동도, 인지 + HUD 동시 구동 시의 여유도 못 쟀다

**상류가 막고 있는 것**

- **`hero_coach` 미구현.** 목 발행 노드가 그 자리를 대신한다. 그 안의 위협
  판정은 방향을 보지 않고 거리만 보므로, 후진 중에 전방 장애물로 경고가 나간다.
  목이므로 고치지 않았다 — 진짜 판정은 `hero_coach`의 몫이다
- **고영우·정재훈 → coach 계약 미정.** HUD가 받는 쪽(`msg/`)은 확정됐지만
  인지가 coach에 무엇을 주는지는 정해지지 않았다
- **조향비 미측정.** CAN은 스티어링 휠 각도를 주는데 모델은 조향륜 각도를 쓴다.
  이 값이 틀리면 코리도 곡률이 통째로 틀린다
- **`msg/TrafficLightMarker.msg`가 죽었다.** `SignalIndicator`로 대체됐고 코드
  어디서도 안 쓰는데 `CMakeLists.txt`에 남아 생성되고 있다. 상류가 이걸 보고
  구현하면 헛수고다. 지워야 한다

**사람이 막고 있는 것**

- **크롬과 월드가 겹친다.** 우측 목표선이 표지판 자리 위를 지난다(13-39).
  운전자가 이상궤적에서 크게 벗어나면 목표선이 화면 가장자리까지 뻗기 때문이고,
  인셋을 걷어낸 배치(13-32)와 맞바꾼 대가다. 실제 화각이 정해진 뒤 영역을
  나눠야 한다
- **밝은 배경에서 눈금이 먼저 죽는다**(13-42). 어두운 배경 18.5%, 흐린 날 2.2%,
  맑은 낮 0%. 흐림이 아니라 배경 휘도 문제이고 모든 요소가 같은 벽에 부딪히지만,
  가장 얕은 요소인 눈금이 가장 먼저 넘어간다. 패널 최대 휘도가 정해지기 전까지는
  이 순서를 바꿀 수 없다
- **저시력 사용자 피드백 0회.** 이 문서의 모든 시각 판단은 시뮬레이션과
  냉독 평가에 기대고 있고, 실제 사용자가 본 적은 없다
- **병인 미확인.** 시력 0.1만으로는 균일한 흐림인지 중심암점인지 알 수 없다.
  중심암점이면 중앙에 정보를 두는 현재 배치가 정확히 최악이 되므로, 배치
  전략이 정반대가 된다. 지금은 균일 흐림을 가정한다
- **표지판이 "버튼"으로 읽힌다**(13-46). 콜드 리드가 도로 표지가 아니라 누르는
  것으로 읽었다. 테두리 있는 사각형 + 글자 하나가 UI 버튼의 형태이기 때문으로
  보인다. 표지 형태를 실제 표지판 윤곽(원/삼각/사각 테두리 색)으로 바꿀지 미정
- **표지판 표시 규칙 미정.** "주차 가능"은 행동 요구가 아니라 녹색 신호와 같은
  부류다. 녹색을 억제한 것과 같은 규칙(행동을 요구할 때만 뜬다)을 표지판에도
  적용할지 정하지 않았다
- **켜진 면적 목표치 미정.** 현재 12~18%가 상한인 것은 확인했지만, 얼마가
  적정인지는 사용자 앞에서만 정해진다
