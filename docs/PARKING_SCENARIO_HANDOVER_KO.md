# 주차 시나리오 인수인계 (2026-11-19 기준)

브랜치 `feat/lidar-parking-scenario`. 다른 컴퓨터에서 이어서 작업하기 위한 문서다.
수치는 모두 11/13 낮 녹화 두 개(`20261113_172234`, `20261113_171835`)에서 잰 값이다.

## 1. 무엇을 만들었나

주행 중 카메라로 주차선·주차칸을 검출하고, 라이다 점유로 빈 칸을 판정하고, 빈 칸에 목표 자세를 놓고
경로를 만들어 HUD에 표시한다.

```
앞 카메라 ─ parking_space_detector ─ /parking/lines (base_link 선)
                                          │
라이다 ─ KISS-ICP ─ /localization/kinematic_state (pose_source:=lidar)
   │                                      │
   └─ /velodyne_packets ─────────► parking_scenario (scenario_node)
                                     선 기억(2 s) → 칸 조립 → 칸 추적(3회 확정)
                                     라이다 점유 격자 → 빈 칸/찬 칸/모름
                                     가장 가까운 확정·빈 칸 → 목표 자세(뒷바퀴 축)
                                          │
                                   planner_node (Hybrid A*) → 경로
                                   display_filter_node → /hero/parking_view (HUD)
```

| 패키지 | 내용 |
|---|---|
| `src/parking/parking_slot_interfaces` | `ParkingSlot`, `ParkingSlotArray` 메시지 |
| `src/parking/parking_slot_mapping` | 선 → 칸 사각형 조립(`geometry.py`), 칸 번호·추적(`registry.py`) |
| `src/parking/parking_scenario` | 시나리오 본체(`scenario.py`), 라이다 점유, 목표 선택, 경로, 표시 필터, 런치 |
| `src/hero/hero_hud`, `hero_coach` | HUD·코치. 바탕화면의 별도 사본을 작업공간에 들여와 수정한 것 (5절 주의 참고) |
| `tools/eval/parking_scenario` | 평가·진단 스크립트, 고정 기준 칸, 선 재생 데이터 |

기준점: 차량의 모든 중심은 뒷바퀴 축이다. 지도 쪽 `base_link`(리그)는 뒷바퀴 축에서 3.61 m 앞이고,
시나리오가 뒷바퀴 축으로 환산한다(`rig_to_rear_axle_m`).

## 3. 작업 규칙 (계속 지킬 것)

- 큰 알고리즘 변경은 "알고리즘 제3자 평가"(별도 검토 에이전트)의 판정을 먼저 받는다. 받은 지적은 다시 묻지 않고 반영한다.
- 통과 기준은 결과를 보기 전에 고정한다. 실패하면 값을 바꿔 다시 시도하지 않고 옵션을 뺀다.
- 모든 수정은 기본 꺼짐 옵션이다. 껐을 때 변경 전과 동일함을 확인한 뒤 커밋한다.
- 실시간은 끔·켬 각 3회로 편차를 본다.
- 라이다는 검증에만 쓴다. 거리에 배율을 곱하는 식으로 라이다에 값을 맞추는 것은 금지다.
- 커밋은 로컬에서 만들고, push는 사용자가 직접 한다(대신 push하지 않는다). 범위는 11/13 낮 녹화다.
- 시험 데이터는 노트북이 아니라 외장 SSD에 쓰고, 시험이 끝나면 지운다(노트북 여유 약 6 GB).

## 4. 평가 방법

- **기준 칸**: 라이다 반사 지도 위에 손으로 줄을 표시해 만든 칸 목록. `reference/`에 고정(sha256).
  172234는 74칸, 171835는 v2 107칸 + 정밀도 전용 2칸.
- **일치**: 칸 중심(입구에서 2.185 m 안쪽) 거리 0.50 m 이하, 방향 10° 이하.
- **지표**: 재현율, 정밀도, 중복, 겹침(IoU 0.2 초과), 빈 칸 오판.
- **실시간 재생은 실행마다 다르다**: 같은 설정에서 일치 칸이 18/22/24로 흔들린다. 그래서 비교는
  결정적 오프라인(검출기 오프라인 + 시나리오 오프라인)을 주로 쓰고 실시간은 3회씩 본다.
- **오프라인 도구의 위치 시각**: 선 시각 직전에 받은 위치를 쓴다(중앙값 0.056 s 늦음). 정확한 시각의 위치로
  바꾸면 일치 칸이 39→32, 55→56으로 달라진다. 지금까지의 수치는 모두 "직전에 받은 위치" 기준이다.

기준선(결정적 오프라인, 옵션 모두 끔):

| 녹화 | 확정 | 일치 | 재현율 | 정밀도 | 빈 칸 오판 |
|---|---|---|---|---|---|
| 172234 | 31 | 27 / 74 | 0.365 | 0.871 | 0 |
| 171835 | 41 | 33 / 107 | 0.308 | 0.805 | 0 |

## 8. 지금까지 알아낸 것

- **어디서 칸을 잃나** (172234, 기준 74칸): 시야 안 70 → 이진화 70 → 허프 52 → 방향 묶음 45 → 선 38 →
  확정 선 34 → 선 3개가 함께 기억에 있음 37 → 칸 후보 32 → 최종 27. 가장 큰 손실은 검출기 앞단이다
  (눈부심 제외 11~17 %, 허프 선분 없음 15~27 %).
- **조립 단계는 범인이 아니다**: 조립 안에서 잃는 칸은 5~12개이고 절반 이상이 "선이 모서리에서 0.45 m 넘게
  못 미침"이다. 어긋난 칸은 조립이 아니라 들어오는 선의 지도 위치가 이미 틀린 경우다.
- **선 위치가 틀리는 조건**: 회전 중(초당 10° 초과에서 후보의 38~79 %가 허용 오차 초과), 측면 5 m 밖.
- **카메라가 라이다보다 약 0.2 m 앞을 본다**: 거리 1.6~5.5 m에서 일정(0.23 m), 지연 탓 아님.
  후보값 `lidar_x_m` −2.51은 보고 전용으로 묶어 두었고 기본값은 −2.71 그대로다.
- **경로 계획**: 탐색 1회가 최대 1초를 막아 주행거리 수신이 밀린다(단일 스레드). 25 m 안에서도
  "search limit" 실패가 남아 있다.

### 11-8. 화면 흔들림, 목표 막힘, 칸 전환 기준 (2026-11-19 추가)

### 11-9. 처리 시간 25 ms 목표 (2026-11-19 추가)

사용자 요구: 노트북은 이 데스크톱보다 훨씬 느리므로 단계별 처리 시간을 25 ms 안으로. 단계별 측정(172234 전체, 이 데스크톱):

| 단계 | 중앙값 | 최대 |
|---|---|---|
| 라이다 한 바퀴 적분(`integrate`) | 4.8 ms | 6.9 ms |
| 위치 콜백(밀린 스캔 처리 포함) | 5.0 ms | 17.3 ms |
| 칸 판정·선택(`step`, 5 Hz) | 3.0 ms | 5.5 ms |
| 선 → 칸 추출 | 0.2 ms | 1.4 ms |
| 경로 탐색(파이썬) | 15 ms | 1000 ms(시간 제한) |

경로 탐색만 문제였다. 탐색 문제 104개(두 녹화의 선택 순간 27개 + 그 뒤 2~8 s 위치에서 다시 탐색)로 비교했다.

| 설정 | 성공 | 중앙값 | 최대 | 25 ms 초과 |
|---|---|---|---|---|
| 파이썬(기존) | 101 (시간 제한 실패 2) | 15.4 ms | 1003 ms | 45 |
| `planner_native` | 103 | 1.5 ms | 50 ms | 3 |
| `planner_native` + `planner_cost_table:=false` + `planner_heuristic_weight:=1.2` | 103 | 1.6 ms | 8.2 ms | 0 |

(남는 실패 1개는 출발 자세 충돌로 설정과 무관하다.)

- **`planner_native`** (기본 false): 탐색 루프와 2D 거리장을 새 패키지 `src/parking/parking_planner_core`(C++, ctypes로 불러옴)에서 돌린다.
  파이썬 코드를 줄 단위로 옮긴 것으로, 104개 문제 전부에서 확장 수와 경로가 파이썬과 같다(자세 차이 1e-9 미만, 기본 탐색 값과
  0.6 / 0.4 값 둘 다). 라이브러리가 없으면 경고를 내고 파이썬 탐색을 쓴다. `tools/build/build.sh`가 `src` 전체를 빌드하므로 노트북에서도 따로 할 일은 없다.
- **`planner_cost_table`** (기본 true = 기존 동작): **기존 코드의 결함을 찾았다.** 장애물 없는 비용표(`kinematic_table`)가 float32로 저장한
  비용을 float64 값과 비교해, 147 000개 자세 중 약 130개만 채우고 끝난다. 나머지는 상수 18.9로 채워져, 목표에서 약 19 m 안에서는
  탐색에 방향이 없었다(비용 순서로 전부 확장). false면 표를 쓰지 않고 장애물을 아는 2D 거리만으로 안내한다: 최대 확장 39 758 → 5 699.
  표를 제대로 채우는 수정(float64)과 기어 방향을 넣은 표도 시험했는데, 빨라지지만 기어 전환이 1.1 → 2.2회로 늘어 넣지 않았다.
- **`planner_heuristic_weight`** (기본 1.5): 표 없이 1.2일 때 기존 대비 경로 길이 평균 +0.07 m, 기어 전환 평균 −0.07회. 1.0은 최대 12 ms, 1.5는 +0.9 m.
- **`planner_time_limit_sec`** (기본 1.0): 안전장치. 조합에서는 0.025.
- 실제 노드, 두 녹화 전체(`run_hud.sh` 기본 조합): 탐색 67 / 76회 모두 성공, 최대 0.01 s(로그 해상도). 같은 조합에서 표를 켠 채
  0.025 s 제한만 걸면 82회 중 26회가 "search limit"로 실패했다.
- `run_fast.sh`: 기준 결과 그대로, 조합(`PNATIVE=1 PTABLE=0 PHW=1.2`)에서 선택 13 / 14회 전부 정답, 경로 전부 성공.
- 하지 않은 것: 노트북에서의 측정, 카메라 선 검출 단계의 시간. 시도했다가 뺀 것: 슬롯 앞 지점 기준 휴리스틱(효과 없음).
- 테스트 `test/test_planner_native.py`(파이썬과 같은 경로, 라이브러리 없으면 건너뜀). 합계 24개 통과.

   느린 노트북에서 예상되는 모습이다(이 데스크톱의 실측은 프레임당 9.4 ms + 디코딩).
5. **틀린 선택은 몇 자리에서 반복된다 (171835).** 7가지 실행 중: 줄 M 1번 자리 5회(0.73~1.01 m, 방향 +8°, 기준에서도 "잘 안 보임"으로 분류한 칸),
   줄 Eo 8번 자리 5회(좌우 +0.52~0.60 m), 줄 Wi 4번 2회(기준은 작은 물체로 "참"인데 빈 칸 판정), 줄 Wo 2번 2회(깊이 −0.6 m).
   줄 Eo를 그려 보면(`docs/evaluation_runs/hud/row_eo_171835.png`, 저장소에는 안 올라감) 칸 안쪽에 비스듬한 가짜 선이 많고, 검출 칸의 폭이
   2.5~2.67 m로 기준(2.40~2.45 m)보다 넓다. 이웃한 진짜 구분선끼리가 아닌 선을 짝지어 칸이 0.5~0.6 m 밀린다.

**탈락: 프레임 시각의 위치를 보간하는 옵션(`parking_detector_pose_sync`).** 프레임을 그 뒤 시각의 위치가 올 때까지 기다렸다 처리하고 위치를 보간한다.
- 1차(실시간 1회, 172234): 미리 정한 기준 "선의 앞뒤 어긋남 0.15 m 초과 비율 절반 이하, 일치 칸 유지" 미달(4.7 → 3.2 %, 일치 25 → 22).
  실시간 1회로는 흔들림과 구분되지 않아 결정적 재현으로 다시 판정했다.
- 2차(결정적 재현, 기준: 두 녹화 모두 일치·정밀도·빈 칸 오판·틀린 선택이 나빠지지 않을 것): 일치 24 → 16, 28 → 27, 틀린 선택 3 → 3
  (그중 하나는 기준에서 "참"인 칸). 기다리는 동안 프레임을 버려 검출이 21~23 Hz로 떨어지는 손해가 더 컸다. 코드는 지우고
  `tools/eval/parking_scenario/pose_sync_option_rejected.patch`로 남겼다.
